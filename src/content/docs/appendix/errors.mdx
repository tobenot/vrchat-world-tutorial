## F.1 Unity Console 编译错

红字停在 Unity 编辑器，不让进 Play Mode。一般是脚本编译过不去。

### `script class cannot be found` / GUID 失效

> `The associated script can not be loaded. Please fix any compile errors and assign a valid script.`

可能原因：
1. Console 上方还有其他红字编译错（脚本编译失败 → 这条是"找不到编译产物"的连锁反应）。
2. `Library/ScriptAssemblies` 目录损坏（Unity 中途崩溃、被杀进程后常见）。
3. 资源 GUID 漂了（手动复制 `.cs` 但没复制 `.meta`，或 git 冲突时把 `.meta` 解错）。

排查步骤：
1. 先把上面其他红字编译错修掉，本错通常自动消失。
2. 如果上面没有别的红字：关闭 Unity，删掉项目根的 `Library/ScriptAssemblies` 文件夹，重开。
3. 如果还在，看出问题的 `.cs` 旁边有没有同名 `.meta`。没有的话从 `git` 历史拉回来。

相关章节：[第 40 章 · 第六节：错误定位表](/surviving/debugging-mindset/#第六节错误定位表)。
相关词条：[`Library/ScriptAssemblies`](/appendix/glossary/#编程基础与-c-语法第-1011-章)、[`.meta` 文件](/appendix/glossary/#版本管理与许可第-8-部)。

### `[UdonSharp] xxx is not exposed in Udon`

> `[UdonSharp] System.IO.File.ReadAllText is not exposed in Udon.`

可能原因：调了不在 VRChat Class Exposure Tree 白名单上的 API。常见的有 `System.IO.*` / `System.Net.*` / `System.Reflection.*` / `System.Threading.*` / `LINQ`。

排查步骤：
1. 打开 `VRChat SDK → Udon Sharp → Class Exposure Tree`，确认目标 API 不在白名单。
2. 按 [附录 D.1](/appendix/udonsharp-limits/#d1-白名单层沙箱拦的) 找替代写法（持久化用 Player Persistence API、外部数据用 `VRCUrl` + `VRCStringDownloader`、列表用 `DataList`，等等）。

相关章节：[第 12 章 · API 开放范围](/programming/udonsharp-personality/#api-开放范围)。
相关词条：[`VRCUrl`](/appendix/glossary/#udonsharp-限制与替代写法第-12-章)、[`Player Persistence API`](/appendix/glossary/#udonsharp-限制与替代写法第-12-章)。

### `Script without UdonSharpBehaviour definition should not have an associated UdonSharpProgramAsset`

可能原因：程序资产指向的脚本没有预期的 UdonSharpBehaviour 定义，或项目存在不匹配的旧资产关联。需检查它是否被错误关联到 UdonSharpProgramAsset。

排查步骤：
1. 核对报错资产关联的源文件、类名、继承关系和程序集设置。
2. 按当前 SDK 工作流修复关联；静态方法支持与目录是不同问题，移入 Plugins 不会绕过 Udon 限制。

相关章节：[第 12 章 · 源码与程序资产的关联](/programming/udonsharp-personality/#源码与程序资产的关联)。
相关词条：[`Plugins/`](/appendix/glossary/#udonsharp-限制与替代写法第-12-章)、[`UdonSharpProgramAsset`](/appendix/glossary/#udonsharp-限制与替代写法第-12-章)。

### `: MonoBehaviour` 报错（脚本基类用错）

> 把外部教程的 C# 文件直接拖进 VRChat 项目，里面写着 `public class Foo : MonoBehaviour`。

可能原因：UdonSharp 项目里能挂上 VRChat 物体并被 Udon 执行的脚本，必须继承 `UdonSharpBehaviour`，不是 `MonoBehaviour`。

排查步骤：
1. 把 `: MonoBehaviour` 改成 `: UdonSharpBehaviour`。
2. 检查脚本里有没有用到 UdonSharp 不支持的 C# 特性（`async`、`yield`、`interface`、自定义泛型……），按 [附录 D.2](/appendix/udonsharp-limits/#d2-编译器层udonsharp-还没支持的-c-特性) 替换。

相关章节：[第 12 章 · UdonSharp 的脾气](/programming/udonsharp-personality/)、[附录 D · UdonSharp 限制](/appendix/udonsharp-limits/)。
相关词条：[`UdonSharpBehaviour`](/appendix/glossary/#编程基础与-c-语法第-1011-章)。

### UdonSharp 编译器特性限制（`async` / `yield` / 接口 / 自定义泛型 / `try-catch`）

> 编译器红字会直接告诉你哪个特性不支持，例如 `UdonSharp does not currently support 'try-catch'`。

可能原因：UdonSharp 编译器自身能力的边界。常见的有 `async` / `await`、`yield return`、自定义泛型、`interface`、`event`、自定义 indexer / operator overload、按「普通数据类」思路 `new` 的对象、`switch` 表达式等。

排查步骤：按 [附录 D.2](/appendix/udonsharp-limits/#d2-编译器层udonsharp-还没支持的-c-特性) 一条条比对，每条都给了替代：
- "过 N 秒做一件事"用 `SendCustomEventDelayedSeconds(nameof(M), N)`。
- 没有 `try-catch` → 写之前判空 `if (x != null)`。
- 没有 `List<T>` / `Dictionary` → 优先 `T[]`，不够用上 `DataList` / `DataDictionary`。

相关章节：[第 12 章 · 语言特性需要逐项核对](/programming/udonsharp-personality/#语言特性需要逐项核对)。
相关词条：[`SendCustomEventDelayedSeconds`](/appendix/glossary/#udonsharp-限制与替代写法第-12-章)、[`DataList` / `DataDictionary` / `DataToken`](/appendix/glossary/#udonsharp-限制与替代写法第-12-章)。

## F.2 Udon 运行时异常

能进世界、Console 没编译错，但脚本一执行就出问题。

### `NullReferenceException` / NRE

> ```text
> NullReferenceException: Object reference not set to an instance of an object
> DoorController.Interact () (at Assets/Scripts/DoorController.cs:18)
> ```

可能原因：
1. Inspector 中被访问的字段未赋有效引用。
2. 调了一个返回 `null` 的方法（`GetComponent<X>()` 没找到 X 组件），没判空就接着用。
3. 引用的对象在运行中被销毁了（这种通常报 `MissingReferenceException`，见下条）。

排查步骤：
1. 双击红字跳到对应 `.cs:行号`，看那一行用了哪个变量。
2. 回 Unity 编辑器看挂这个脚本的 GameObject，Inspector 里那个变量对应的引用槽是不是 `None`。
3. 如果是 `GetComponent` 之类的返回值，加 `if (x != null)` 提前判空（参考 [第 40 章 · 第六节：错误定位表](/surviving/debugging-mindset/#第六节错误定位表)）。
4. UdonSharp 不支持用 try/catch 恢复这类异常。当前执行会中断，UdonBehaviour 还可能进入 halted 状态；需看客户端日志，而非只根据按钮表现推断。

相关章节：[第 40 章 · 第一节：读取 Console](/surviving/debugging-mindset/#第一节读取-console)。
相关词条：[`NullReferenceException` / NRE](/appendix/glossary/#调试与测试第-8-部)。

### `UdonBehaviour will be halted`（Udon VM 异常自停）

> ```text
> Error - [UdonBehaviour] An exception occurred during Udon execution,
> this UdonBehaviour will be halted.
> VRC.Udon.VM.UdonVMException: An exception occurred during EXTERN to
> 'VRCSDK3VideoComponentsBaseBaseVRCVideoPlayer.__GetTime__SystemSingle'.
> ---> System.NullReferenceException: ...
> ```

可能原因：当前 `UdonBehaviour` 抛了未捕获异常。异常可使该客户端上的 UdonBehaviour 停止执行。依赖它的显示或同步流程也可能受影响，修复并重新构建测试后核对恢复情况。

如果交互先能运行、随后停止，可检查两次操作之间是否出现 halted；也要排查对象禁用、状态条件和引用变化。

排查步骤：
1. 在发生异常的客户端本次 `output_log_*.txt` 中搜索 `halted`；Unity Console 可显示 UdonSharp 异常监听器转回的客户端记录，但不能把编辑器没有红字当作客户端没有异常。日志位置与启动参数见[调试方法](/surviving/debugging-mindset/#第三节查找-udon-的-halted-记录)。
2. 读 `--->` 后面的 `InnerException`，确定具体异常类型。
3. 堆栈里 `EXTERN to '...'` 那条会指出失败的外部 API 调用。结合调用上下文定位引用、索引或参数；上面的样本是空引用，不代表所有 halted 都由空引用引起。
4. 按根因修复：空引用检查 Inspector 接线并增加有效性判断，越界检查数组长度与索引，其他异常按具体 API 条件处理。在测试副本中重新执行同一组操作，核对日志与结果。官方说明见[调试 Udon 项目](https://creators.vrchat.com/worlds/udon/debugging-udon-projects/)。

相关章节：[第 40 章 · 第三节：查找 Udon 的 halted 记录](/surviving/debugging-mindset/#第三节查找-udon-的-halted-记录)。
相关词条：[halted](/appendix/glossary/#调试与测试第-8-部)、[EXTERN](/appendix/glossary/#调试与测试第-8-部)。

### `MissingReferenceException`

> `The object of type 'GameObject' has been destroyed but you are still trying to access it.`

可能原因：代码里 `Destroy(...)` 了一个对象，之后又通过原引用调用它。Unity 引用槽里的"对象已销毁"和 C# 的 `null` 不完全一样——它是一个伪 null（`x != null` 也可能被判为 `false`）。

排查步骤：
1. 检查 Destroy 之后是否仍使用该对象。SetActive(false) 只禁用对象，不等于销毁引用。
2. 需要反复启用的场景对象可使用 SetActive(false)；确需销毁时同步清理引用与依赖。
3. 引用清空时显式赋 `null`：`target = null;`。

相关章节：[第 40 章 · 第六节：错误定位表](/surviving/debugging-mindset/#第六节错误定位表)。

### `Cannot find method '...' on UdonBehaviour`

> `[Udon] Cannot find method 'OnButtonPress' on UdonBehaviour 'GameButton (UdonBehaviour)'`

可能原因：
1. `SendCustomEvent("OnButtonPress")` 字符串方法名拼错了（少了大小写、写错了字母）。
2. 目标方法是 `private` 的——`SendCustomEvent` 只认 `public` 方法。
3. 目标脚本上根本没这个方法。

排查步骤：
1. 把字符串方法名换成 `nameof(OnButtonPress)`——改名后编译器立刻提示，不用等运行时。
2. 检查目标方法的可见性：要被 `SendCustomEvent` / `SendCustomNetworkEvent` 调用的方法必须 `public`。
3. 跨脚本调用时确认方法在的是不是你 Inspector 里拖的那个 GameObject。

相关章节：[第 12 章 · 运行时对象与组件](/programming/udonsharp-personality/#运行时对象与组件)、[附录 D.3 · 运行时行为差异](/appendix/udonsharp-limits/#d3-工程化层脚本布局生命周期运行时行为)。
相关词条：[`SendCustomEvent`](/appendix/glossary/#多人同步所有权网络事件manager-模式第-2630-章)、[`nameof()`](/appendix/glossary/#拿取座椅镜子animator第-1517-章)。

### 按按钮没反应（不报错也不打日志）

可能原因：
1. 按钮所在 GameObject 没装 `Collider`，或装了但 `Is Trigger` 和 `Interact` 的预期不匹配。
2. 脚本没真的挂上去，或挂错了对象。
3. 脚本上一次跑到一半就 halted 了——所以**这一次根本没触发任何事件**。
4. `Interact` 在 VRChat 里写法是 `public override void Interact()`，签名不匹配时不能依赖其作为预期事件入口，需按 SDK 定义修正。

排查步骤：
1. 在 `Interact()` 第一行加 `Debug.Log("[Door] Interact 被触发");`，再 Build & Test。日志没出来 = 事件根本没到；出来了 = 事件到了但中间断了。
2. Console 搜 `halted`，看有没有上一次留下的红字。
3. 检查方法签名：Unity 标准方法（`Start` / `Update`）不写 `override`；VRChat 事件（`Interact` / `OnPickup` / `OnPlayerJoined`）必须写 `public override`。

相关章节：[第 13 章 · Interact 的组件和输入条件](/come-alive/press-and-light/#interact-的组件和输入条件)、[第 40 章 · 第二节：在执行边界记录日志](/surviving/debugging-mindset/#第二节在执行边界记录日志)。

### 协程不工作 / `yield return new WaitForSeconds(...)` 编译过不去

可能原因：UdonSharp 不支持 `yield`，普通 Unity 教程里的协程写法在这里走不通。

排查步骤：把协程改成 `SendCustomEventDelayedSeconds`：

```cs
// 普通 Unity 协程
IEnumerator MyCoroutine()
{
    yield return new WaitForSeconds(1f);
    DoNext();
}

// UdonSharp 替代
public void DoLater()
{
    SendCustomEventDelayedSeconds(nameof(DoNext), 1f);
}
public void DoNext() { /* ... */ }   // 必须 public
```

相关章节：[第 12 章 · 语言特性需要逐项核对](/programming/udonsharp-personality/#语言特性需要逐项核对)、[附录 D.5 替代写法对照](/appendix/udonsharp-limits/#d5-替代写法对照)。
相关词条：[`SendCustomEventDelayedSeconds`](/appendix/glossary/#udonsharp-限制与替代写法第-12-章)。

## F.3 同步与多人

表现差异出现在不同客户端之间。先去 [附录 E · 网络同步决策表](/appendix/networking-decision/) 用 [E.7 常见错配的对照](/appendix/networking-decision/#e7-常见错配的对照)对一眼，下面只列那张表上没展开的细节。

### 自己看到效果，别人没看到

可能原因：脚本里改的是本地字段，没走网络。

排查步骤：
1. 字段加 `[UdonSynced]`。
2. 脚本类上加 `[UdonBehaviourSyncMode(BehaviourSyncMode.Manual)]`（或 `Continuous`）。
3. 改完字段后调 `RequestSerialization()`。
4. 非 Owner 在 `OnDeserialization()` 里读新值并刷新本地表现。

相关章节：[第 28 章 · Manual 状态同步的四个部分](/with-others/tell-everyone/#manual-状态同步的四个部分)、[附录 E.2.2](/appendix/networking-decision/#e22-一个状态字段开关计数回合玩家选择)。

### 改字段过一会儿被盖回去

可能原因：改字段的人不是 Owner——他改的值只在本机有效，Owner 那份的值下次同步过来就会盖掉。

排查步骤：改字段前先 `Networking.SetOwner(Networking.LocalPlayer, gameObject)`，然后再改 `[UdonSynced]` 字段 + `RequestSerialization()`。或者发 `SendCustomNetworkEvent(NetworkEventTarget.Owner, "改字段的方法")` 让 Owner 自己改。

相关章节：[第 27 章 · 交互时请求所有权](/with-others/ownership/#交互时请求所有权)、[附录 E.3.2 什么时候要 SetOwner](/appendix/networking-decision/#e32-什么时候要-setowner)。

### 后来加入的人看不到当前状态

可能原因：状态是用 `SendCustomNetworkEvent` 广播出去的——Late Joiner 收不到那次广播。

排查步骤：把"事件"翻译成"状态字段"。例如把"游戏开始过没有"做成 `[UdonSynced] bool gameStarted`，进 `OnDeserialization` 时刷 UI。无参数广播不会复制 Owner 的本地变量；持久状态应由同步字段保存。

相关章节：[第 29 章 · 状态与历史事件](/with-others/late-joiners/#状态与历史事件)、[附录 E.5.2](/appendix/networking-decision/#e52-修法把事件翻译成状态)。

### `RequestSerialization()` 调了但别人没收到

可能原因：调用者不是 Owner——`RequestSerialization` 只有 Owner 调用才有效。

排查步骤：方法开头加 `if (!Networking.IsOwner(gameObject)) return;`。想让谁来改就先 `SetOwner` 给谁。

相关章节：[第 28 章 · 同步灯开关](/with-others/tell-everyone/#同步灯开关)、[附录 E.7](/appendix/networking-decision/#e7-常见错配的对照)。

## F.4 Build & SDK 上传

### 顶部菜单找不到 `VRChat SDK`

可能原因：项目模板不是 World，或者 Worlds SDK 包没装好。

排查步骤：
1. 关闭 Unity，回 VCC（VRChat Creator Companion）打开项目。
2. 检查项目类型是 `World`，不是 `Avatar`。
3. 在 VCC 核对 Worlds SDK 已安装且版本与项目兼容；更新前保留备份。

相关章节：[第 4 章 · 第三步：创建 World 项目](/getting-started/tools/#第三步创建-world-项目)、[第 5 章 · Build & Test 不工作时的检查清单](/getting-started/first-world/#第五步build--test)。

### SDK 控制面板缺少 Scene Descriptor

> SDK 控制面板顶部红字：场景里没有 `VRC Scene Descriptor`。

可能原因：当前打开的场景里没挂 `VRC Scene Descriptor` 组件。

排查步骤：
1. Hierarchy 里检查有没有名为 `WorldDescriptor`（或类似）的 GameObject，身上是不是真挂了 `VRC Scene Descriptor`。
2. 没有的话：新建一个空物体，`Add Component → VRC Scene Descriptor`，把 Spawn 拖进 `Spawns` 数组的第 0 槽。
3. 检查当前打开的场景是否就是构建目标。

相关章节：[第 5 章 · 第四步：添加场景描述组件](/getting-started/first-world/#第四步添加场景描述组件)。
相关词条：[`VRC Scene Descriptor`](/appendix/glossary/#玩家落地世界-ui跨世界传送门第-31--34--35-章)、[`Spawns 数组`](/appendix/glossary/#玩家落地世界-ui跨世界传送门第-31--34--35-章)。

### 进世界后一直往下掉

可能原因：
1. `Floor` 身上的 `Box Collider` 被删掉了 / 关闭了。
2. `Spawn` 的 Y 值落到地板下面去了。
3. `Floor` 物体本身被禁用（Inspector 顶部的勾掉了）。

排查步骤：
1. 选中 Floor，确认用于承重的 Collider 已启用且未勾 Is Trigger。
2. 选中 Spawn，看 Transform 的 Y 是不是在 Floor 上方一点点（如 `0.1` 而不是 `-1`）。
3. Build & Test 试。

相关章节：[第 5 章 · Build & Test 不工作时的检查清单](/getting-started/first-world/#第五步build--test)。

### 点了 Build & Test 没反应

可能原因：
1. SDK 控制面板里没登录 VRChat 账号。
2. 本机没装 VRChat 客户端（Steam 版或官方版都行）。
3. 顶部 Build Target 切到了 Android 但本机 VRChat 是 PC 版。

排查步骤：
1. SDK Control Panel 顶部 `Authentication` 标签，登一下账号。
2. 顶部菜单 `File → Build Settings`，确认 `Platform` 是 `Windows, Mac, Linux`（PC 版）。
3. 确认本机 VRChat 客户端能正常启动。

相关章节：[第 5 章 · Build & Test 不工作时的检查清单](/getting-started/first-world/#第五步build--test)、[第 41 章 · 第三节：Build & Test](/surviving/testing-your-world/#第三节build--test)。

### SDK Validation 红字（上传前）

> Builder 列出检查消息；以实际报错对象、级别和目标平台为准。

可能原因：必需组件或项目设置缺失、脚本编译失败、资源不兼容，或存在平台性能警告。纹理超过 1K、面数偏高等不应一概写成世界上传硬错误。

排查步骤：
1. 一条条点 Validation 里的红字，下方 `Auto Fix` 能修的就修。
2. 不能 Auto Fix 的，按红字定位的对象修。
3. 分别核对 PC 与 Android 结果，区分阻塞错误与建议，参见 [第 39 章 · 分清硬限制与建议](/placeness/pc-and-quest/#分清硬限制与建议)。

相关章节：[第 41 章 · 第五节：上传版本的受限测试](/surviving/testing-your-world/#第五节上传版本的受限测试)、[第 44 章 · 第一节：上传条件与项目检查](/publishing/submit-your-world/#第一节上传条件与项目检查)。
相关词条：[`SDK Validation`](/appendix/glossary/#调试与测试第-8-部)、[Community Labs](/appendix/glossary/#发布商业化与运营第-9-部)。

### `This world has no Quest version`（玩家端报错）

可能原因：上传时只 Build 了 PC 平台，Quest 端的 Quest 玩家进不来。

排查步骤：
1. `File → Build Settings → Switch Platform → Android`。
2. 等 Unity 重新导入资源（中等大小项目几分钟到十几分钟）。
3. SDK Control Panel → `Build & Publish` 一次。
4. 验证：进 VRChat 网页 / 客户端，世界详情应同时显示 `PC` 和 `Android` 两个平台徽章。

相关章节：[理解章 A · 跨平台 PC、Android（含 Quest）、iOS 各一份](/getting-started/world-pipeline/#目标平台分别构建)、[第 39 章 · 一份工程里的平台差异](/placeness/pc-and-quest/#一份工程里的平台差异)。

## F.5 资源、材质、Quest

### 材质突然变粉色

可能原因：Shader 丢失。Unity 在找不到对应 Shader 时用 Error Shader（紫粉色）兜底。常见情形：换平台后 Shader 不兼容、复制工程时 Shader 路径漂了、Shader 文件被误删。

排查步骤：
1. 选中变粉的 Material，看 Inspector 顶部 `Shader` 栏，检查是否为错误 Shader、缺失引用或编译失败。
2. 用于隔离问题的测试：把 Shader 切回 `Standard`（PC）或 `VRChat/Mobile/Standard Lite`（Quest）。
3. 根因：Project 里搜原本的 Shader 文件还在不在；不在的话从素材包重新导入。

相关章节：[第 9 章 · 修改没有生效时](/workbench/materials-light/#修改没有生效时)、[第 39 章 · 材质与 Shader](/placeness/pc-and-quest/#材质与-shader)。
相关词条：[Shader](/appendix/glossary/#渲染材质与贴图进阶)、[VRChat Mobile Shader](/appendix/glossary/#quest-与跨平台第-39-章)。

### 烘焙后场景全黑 / 全白

可能原因：
1. Light Mode 设置和场景里物体 `Static` 标记不一致。
2. 没有任何 `Mixed` 或 `Baked` 光，且关掉了 `Auto Generate`。
3. Lightmap 还没烘焙完成。
4. 当前 Shader 不支持所选光照模式，或目标平台上的光照数据不正确。

排查步骤：
1. 检查是否有预期的实时、烘焙或环境光源；为需要参与烘焙的 Renderer 配置 Contribute GI 和有效 UV。
2. `Window → Rendering → Lighting → Generate Lighting`，等烘焙完成。
3. Android：核对目标 Shader 支持的 Lighting Mode，参考 [第 39 章 · 灯光配置](/placeness/pc-and-quest/#灯光配置)。

相关章节：[第 36 章 · 生成 Lightmap](/placeness/light/#生成-lightmap)、[第 39 章 · 灯光配置](/placeness/pc-and-quest/#灯光配置)。
相关词条：[Lightmap](/appendix/glossary/#渲染光照进阶)、[Subtractive](/appendix/glossary/#渲染光照进阶)。

### Quest 上传被拒：纹理 / Shader / Triangle 数超规

先读取准确错误。Android 世界的压缩包体限制与性能建议不同；不能把头像 Shader 白名单或面数评级直接套到世界。

排查步骤：按 SDK Validation 的具体提示一条条修：
1. **纹理**：超过 1K 的批量改 `Max Size = 1024` 或 `512`（Texture Inspector 顶部），移动端包体还要压到 100 MB 以内。
2. **Shader**：把高成本或 PC 专用 Shader 优先替换为移动端友好的 `Mobile/VRChat/Lightmapped` 或 `VRChat/Mobile/*` 系列。
3. **Triangle**：Mesh 用 Mesh Decimator 或建模软件减面。
4. 整体读 [第 39 章 · 分清硬限制与建议](/placeness/pc-and-quest/#分清硬限制与建议) 和 [第 44 章 · 第一节：上传条件与项目检查](/publishing/submit-your-world/#第一节上传条件与项目检查)。

相关章节：[第 39 章](/placeness/pc-and-quest/)、[第 44 章 · 第一节：上传条件与项目检查](/publishing/submit-your-world/#第一节上传条件与项目检查)。
相关词条：[ASTC](/appendix/glossary/#quest-与跨平台第-39-章)、[VRChat Mobile Shader](/appendix/glossary/#quest-与跨平台第-39-章)。

### 帧率掉到 30 以下 / Stats 红色

可能原因，按测量结果核对：
1. **Draw Call / Batches 过高**——材质数太多，没启用 GPU Instancing / Static Batching。
2. **实时光太多**——烘焙适用的静态光照，动态物体用 Light Probe 获取环境照明。
3. **镜子 / VideoPlayer 单独算账**——镜子增加反射渲染；视频播放器增加解码、纹理与音频开销，两者机制不同。
4. **Overdraw 高**——半透明物体堆叠。

排查步骤：
1. `Game` 面板右上 `Stats`，记下 `Batches` / `SetPass calls` / `Tris` / `Verts`。
2. `Window → Analysis → Profiler` 进 Play Mode，看 CPU / GPU 栏哪条最高。
3. 按 [第 38 章 · 按测量结果确定优化顺序](/placeness/performance/#按测量结果确定优化顺序) 一条条对。

相关章节：[第 38 章 · 全章](/placeness/performance/)、[第 36 章 · 实时灯与烘焙灯共同使用](/placeness/light/#实时灯与烘焙灯共同使用)。
相关词条：[Draw Call / Batches](/appendix/glossary/#渲染性能第-38-章)、[GPU Instancing](/appendix/glossary/#渲染性能第-38-章)、[Profiler](/appendix/glossary/#渲染性能第-38-章)。

## F.6 工具链 / 环境

### VCC 找不到 Unity / 启动卡在右下角 / Console 红字一片（首启动卡点）

排查步骤：直接对 [第 4 章 · 启动问题检查](/getting-started/tools/#启动问题检查)。常见三类：
- VCC 找不到 Unity：手动指定 `Unity Hub → 安装 → 添加 → 选官方指定版本`。
- 导入长时间未完成：先查看 Editor.log、磁盘空间和当前导入任务；确认缓存问题后，关闭 Unity 并备份项目，再重建可再生缓存。
- Console 连续报错：先处理第一条有效错误，并核对 VCC 的 Unity / SDK 版本。

相关章节：[第 4 章 · 启动问题检查](/getting-started/tools/#启动问题检查)。

### `MAX_PATH` / 中文路径 / 文件存在但读不到 / `.meta` 找不到对应资源

可能原因：Windows 默认路径长度上限 260 字符，VRChat 项目里 `Library/` 下的缓存路径 + 资产相对路径加起来很容易撞上限。表现是部分 `.meta` "看着在但 Unity 找不到对应资源"、Material 引用混乱。

排查步骤：
1. 把项目挪到短路径下，如 `D:\vrc\MyWorld` 而不是 `C:\Users\长用户名\OneDrive\桌面\VRChat 项目\我的世界\`。
2. 按错误确认是否为路径长度、权限、锁文件或具体工具的字符兼容问题；中文路径不意味着 .NET 本身不支持。
3. Windows 10 1607+ 可以全局开 `LongPathsEnabled` 注册表项，但还需应用显式支持长路径；缩短项目目录不依赖这一能力。

相关章节：[第 4 章 · 第三步：创建 World 项目](/getting-started/tools/#第三步创建-world-项目)。
相关词条：[`MAX_PATH`](/appendix/glossary/#工具链与项目)。

### Library 损坏 / 切平台后 Unity 不正常

> 切到 Android 后场景一片粉、Console 飘红、Material 引用全乱。

可能原因：Unity 的 `Library/` 目录是平台相关的二进制缓存。切平台时 Unity 会重建一部分缓存；过程中崩溃 / 杀进程会让 `Library/` 处于半损坏状态。

排查步骤：
1. 关闭 Unity。
2. 删除项目根的 `Library/` 整个目录（**不要删 `Assets/` / `Packages/` / `ProjectSettings/`**）。
3. 重开 Unity，让它从头构建 Library（5–30 分钟，看项目大小）。
4. `Library/` 已在 `.gitignore` 里，删了不影响 git 仓库。

相关章节：[第 42 章 · 第二节：配置 .gitignore](/surviving/version-control/#第二节配置-gitignore)。
相关词条：[`Library/ScriptAssemblies`](/appendix/glossary/#编程基础与-c-语法第-1011-章)、[`.gitignore`](/appendix/glossary/#版本管理与许可第-8-部)。

### 场景 `.unity` 文件 git 冲突难合

可能原因：`.unity` 是 YAML 格式但内部全是 GUID 引用、行号细碎，普通 `git merge` 处理不好。

排查步骤：
1. 打开 `Edit → Project Settings → Editor`，把 `Asset Serialization Mode` 设为 `Force Text`。
2. 配 Git 用 UnityYAMLMerge 处理 `.unity` 和 `.prefab` 的合并。
3. 团队协作时按"一个场景同一时间只一个人改"原则降低冲突频率。

相关章节：[第 42 章 · 第一节：Unity 的序列化与 .meta](/surviving/version-control/#第一节unity-的序列化与-meta)、[第 42 章 · 第五节：合并场景和 Prefab](/surviving/version-control/#第五节合并场景和-prefab)。
相关词条：[Smart Merge / UnityYAMLMerge](/appendix/glossary/#版本管理与许可第-8-部)。
