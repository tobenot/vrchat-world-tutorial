GameObject、Component、Prefab、Material 和 Light 不在同一层级。GameObject 是场景对象，Component 附着在对象上；Material 是被 Renderer 引用的资源；Light 是组件；Prefab 是保存对象层级和配置的资源。

## GameObject 组织组件

对象名称用于辨认，具体行为由组件和字段决定。`Floor` 有网格和 Renderer 时可见，有合适的 Collider 时能提供碰撞，Transform 决定这些形状的位置与缩放。

```text
Floor（GameObject）
├─ Transform
├─ Mesh Filter → 网格资源
├─ Mesh Renderer → 材质资源 → Shader 与贴图
└─ Box Collider
```

这解释了[渲染与碰撞对照实验](/workbench/gameobjects/)：禁用 Renderer 后物体仍可碰撞，因为 Collider 没有随之被禁用。

## 组件组合表达不同需求

一个灯具可以包含模型、Light 和 Collider；一个座位可以包含模型、Collider 与 VRC Station。不同对象可以复用相同组件，不需要引擎为每一种组合定义专用对象类型。

组件也有依赖和使用条件。Mesh Renderer 需要网格和材质，物理行为需要合适的碰撞和刚体设置，SDK 组件必须符合 VRChat 的支持范围。把组件加到对象上只是配置的开始，实际行为还取决于字段、引用和运行环境。

## Prefab 保存组合与共有配置

[Prefab 章](/workbench/prefabs/)把球体、Point Light 和相关设置保存为 `GlowBall.prefab`。场景里可以有多个实例，每个实例保留自己的位置，并继承未被覆盖的资源属性。

```text
GlowBall.prefab（资源）
    ├─ 场景实例 A：位置 A，使用共有 Light 参数
    └─ 场景实例 B：位置 B，颜色有单独 Override
```

Prefab 不是挂在 GameObject 上的一种组件。实例与资源的联系用于编辑阶段的复用，也不会自动成为多人状态同步。

## 材质、光源与发光外观

Material 保存 Shader 参数，Light 提供光照计算。材质的 Emission 可以使表面自亮，但它与实时 Light 是不同机制。启用适用的全局光照设置并烘焙后，发光材质也可以把贡献写入光照数据。

因此，如果球体亮而墙面不亮，要区分当前是否只有 Emission、是否有实际照到墙的 Light，以及是否存在有效的烘焙光照。不能只用「有没有 Light」概括所有发光贡献。

## 按现象检查对应配置

如果照着配置步骤做了，但物体仍没有预期行为，可以逐项核对：

1. **位置或尺寸不对**：查看 Transform、父级变换和局部坐标。
2. **应该可见却没有显示**：查看物体激活状态、Renderer、网格、材质和摄像机可见条件。
3. **应该阻挡却能穿过**：查看 Collider 是否启用、是否为 Trigger，以及碰撞层设置。
4. **声音或光照不符**：查看 Audio Source、Light、相关资源和作用范围。
5. **交互没有响应**：查看目标组件、触发条件、程序编译状态、事件日志和引用槽。
6. **实例与预期参数不同**：查看 Prefab 资源和该实例的 Override。

这些是检查入口，不是所有问题的完整清单。一次修改一个条件，再用相同操作复现，才能确认修改是否解决了问题。

## 从需求到配置

「房间角落有一个可见且能照亮墙面的灯球」可以拆成：球体网格、Renderer 和材质负责外观；Point Light 负责本例的实时照明；Transform 决定位置；Prefab 管理重复实例。

拆分后，每项配置都有对应的作用和检查方法。没有提出玩家操作需求时，这个对象也不需要额外的自定义交互脚本。

如果需求增加为「按按钮开关这盏灯」，清单就增加按钮 Collider、包含 Interact 的 UdonSharp 脚本，以及指向这盏 Light 的引用槽。对应的创建、挂载、赋值和客户端检查见[灯光开关](/come-alive/press-and-light/#第二步创建灯光开关脚本)。增加的是输入与控制关系，不是把 GameObject 换成一种专用的「按钮灯」类型。
