维护包括处理反馈、修复问题、更新依赖和保存可恢复版本。是否继续增加内容由作品用途与维护安排决定。静态展厅、完成的短篇或活动存档，可以在不持续添加交互的情况下保留。

## 第一节：建立可用的反馈入口

在世界说明或场内标牌提供一个实际有人处理的联系方式，例如论坛、问题表单或社群反馈频道。入口与更新公告可以使用同一渠道，不需要按访客人数强制建立多个平台。

标牌可以列出地址或联系方式。不要用未经核实的 `Networking.OpenURL` 代码承诺一键打开站外页面；实现外链前核对当前 SDK 的支持接口和限制。

如果使用社群服务器，可从四个频道开始，按实际需要合并或省略：

```text
公告：版本、已知问题和维护范围
反馈：按报告模板收集问题与处理结果
闲聊：日常交流
活动：时间、参加方式与变动通知
```

在 World Description 写清实际反馈入口，例如“问题反馈：【可访问的反馈页面】；请附平台和世界版本”，保存后从世界详情页核对。没有活动就不必设置活动频道，也不需要达到固定人数才提供反馈入口。

问题报告包含：

```text
世界名称 / World ID：
世界版本：
平台与设备：
问题发生位置：
操作步骤：
预期结果：
实际结果：
是否能重复：
相关截图或日志片段：
```

不要要求玩家公开整份含个人信息的日志。先收集与问题有关的片段，再根据实际需要补充条件。

## 第二节：按影响安排处理

| 类别 | 处理依据 |
| :--- | :--- |
| 无法进入、持续报错、关键数据受损 | 确认影响版本与范围，优先恢复可用状态 |
| 关键操作失效、严重性能或平台兼容问题 | 记录复现条件，安排修复与目标设备验证 |
| 标识不清、文字缺字、音量失衡 | 根据任务影响与可替代路径排期 |
| 新功能与风格建议 | 比对项目用途、实现和维护成本 |

反馈数量不是唯一优先级。一个只出现一次但能导致保存数据丢失的问题，可能比多个装饰建议更急。没有复现的报告保留证据与状态，不直接标为已解决。

设计建议可以接受、暂缓或拒绝。说明决定对应的范围与原因即可，不推测提出建议者的动机，也不用固定的 30% / 70% 开发时间比例衡量合理性。

## 第三节：更新记录与 World ID

[第 44 章](/publishing/submit-your-world/)区分了世界资产和实例。更新原世界要保留其 World ID；同一 ID 的常规更新保留原有链接和相应统计，不需要重新创建一座世界。

发布记录至少包含：源码 commit、Unity / SDK 版本、平台构建、World ID、日期、测试结果和已知问题。面向玩家可以另外使用 `v1.2` 这样的版本名；它与平台内部的上传版本记录不是同一概念。

更新说明示例：

```text
v1.2
- 修复 Android 端门牌缺字
- 调整出生点，避免落在椅背中
- 已测试：Windows 桌面、PC VR、独立 Quest
- 已知问题：外部视频源偶发加载失败，可使用重试按钮
```

说明只列实际验证内容，不把一次单人测试描述成“所有平台稳定”。

## 第四节：修复与回退

线上问题的处理流程：

1. 记录影响范围，必要时通知使用者；未知完成时间就不作具体承诺。
2. 从对应源码版本建立修复，先验证复现用例。
3. 对受影响平台重新构建，检查目标 World ID 后上传。
4. 创建新实例，通过版本标记确认新内容，再执行原始失败步骤。
5. 发布修复结果及仍未解决的范围。

正在运行的实例不会因为上传完成就成为新版本。通知玩家加入已确认的新实例；仅退出后重进同一个旧实例不能作为升级验证。

若新版本引入严重回归，可从已记录的稳定源码和依赖恢复、测试并重新上传。Git 回退不会自动回退平台内容，上传也不会自动恢复已经改变的持久化数据。

## 第五节：大改与数据迁移

大改不一定必须新建世界。比较两种方案的影响：

- 沿用 World ID：保留入口和数据范围，但要处理旧存档、共享对象及跨平台兼容。
- 新建 World ID：明确区分作品版本，但收藏入口和持久化数据不会自动迁移，需要单独说明。

选择前列出变化：移除功能、调整布局、付费权益、存档格式与依赖。对已经承诺的商品或活动，核对相应义务。

PlayerData 键和值的格式变化要有迁移策略。缺失字段使用明确默认值，不因更新而无提示覆盖已有进度。新旧平台构建并存时，也要检查数据是否兼容。

## 第六节：读数据时保留定义

世界页面或授权工具能提供哪些数据，就记录哪些数据，并保存获取日期和定义。不要假定官方一定提供每日曲线、平均会话时长或分平台留存。

- **Visits** 不是已确认的独立用户数。
- **Favorites** 表示收藏相关统计，不能单独证明回访。
- **Favorites / Visits** 只能是这两个计数的比值，不是留存率。
- 留存需要有明确用户群、时间窗口和再次访问数据；缺少这些条件就不能计算。

比较版本时，活动、推广、上线时间和平台变化都可能影响访问数据。数据下降不能直接归因于世界质量或某一个功能。

测试完成率、可复现问题数量、活动是否顺利执行等也可以作为项目指标。不按固定访问量给世界或作者划分“健康”“成功”等等级。

## 第七节：维护范围与存档

维护状态可以具体写为：

- 继续开发新内容，并处理问题。
- 仅处理严重错误与必要兼容性问题。
- 作为存档保留，不再提供修复承诺。
- 因授权、运行或其他原因暂时下线。

如果状态改变，在原有说明和反馈渠道注明生效时间、剩余支持范围及有效联系入口。没有计划处理所有错误时，不写“严重问题仍会修”作为默认承诺。

保留工程、依赖、许可和最后一次可用构建的记录。作品完成或停止更新本身不表示失败，也不能从低访问量推断作者或社群的状态。

## 两项定期记录练习

周期按自己的维护安排确定；下面的每周、每月是可选起点，不构成持续更新承诺。

1. 每周选一次时间查看已经公布的反馈入口。把重复报告合并到同一问题，补齐受影响版本、复现条件与处理状态；按影响分类，并为要处理的项写下下一步。未复现的保留为待查，已修的附上复测版本与结果。
2. 每月把有权限取得的同口径数据记入同一份记录，例如采集日期、World ID、页面显示的 Visits / Favorites，以及两次采集的差值。另记期间发布、社群活动和入口变化。没有某项数据就写“未取得”，社群活动人数单列，不能代替世界访客数或留存率。

例如一行记录可写“2026-10-01；World ID：【实际 ID】；Visits：【页面计数】；Favorites：【页面计数】；来源：【实际页面】；本期发布：v1.2；活动：一次；未取得独立访客与回访数据”。下次在相同来源记录后比较变化，注明统计定义变化或重置；不要用一次涨跌断定改版有效。

## 维护检查表

- [ ] 每条待处理问题有影响、版本和复现状态
- [ ] 本次修改与商品 / 世界说明一致
- [ ] 数据迁移与跨平台兼容已检查
- [ ] 发布记录关联到准确源码和 World ID
- [ ] 新实例加载的版本已验证
- [ ] 回退资料和反馈入口可用
- [ ] 对外说明的维护范围与实际安排一致
