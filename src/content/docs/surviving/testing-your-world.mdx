[第 40 章](/surviving/debugging-mindset/)中的日志方法用于定位具体问题。测试则检查一组明确的预期：哪些功能应当发生、谁应当看到、在什么平台和条件下成立。

## 第一节：分层测试

| 环境 | 适合检查 | 不能据此确认 |
| :--- | :--- | :--- |
| Unity + ClientSim | 本地交互、引用、UI 和状态逻辑 | 真实多人时序、设备性能、VR 舒适度 |
| Build & Test | 构建后的真实客户端行为、多客户端状态 | 不同网络和设备的全部条件 |
| 上传后创建受限访问实例 | 下载、账号差异、真实参与者与网络 | 没有参加测试的平台和人数 |
| 目标设备 | 该设备上的渲染、操作、音视频和性能 | 其他型号或不同显示设置 |

每次测试记录版本、Unity / SDK 版本、客户端、设备、人数和结果。“通过”只适用于已执行的用例与条件。

## 第二节：ClientSim

Worlds SDK 附带 ClientSim，可在 Unity 的 Play Mode 中模拟部分 VRChat 交互。保存场景后进入 Play，检查行走、Interact、Pickup、Station 和 UI；同时在 Inspector 和 Console 观察脚本状态。

Remote Player 是编辑器中的模拟对象，不是另一个通过真实网络连接的客户端。它不能验证两台设备之间的所有权竞争、同步延迟或真实后加入流程。

持久化工具可辅助观察 PlayerData / PlayerObject，但重新加入、恢复顺序和不同玩家的数据隔离仍要在客户端确认。编辑器中能执行某个 API，也不代表其客户端条件已满足。

ClientSim 使用编辑器的渲染和输入环境。桌面视角不能替代头显中的可读性、伸手操作或移动舒适度测试。

## 第三节：Build & Test

打开 `VRChat SDK → Show Control Panel`。确认 Authentication 已登录，并在 Settings 中检查 VRChat 客户端路径。Builder 中先处理阻止构建的错误。

当前 SDK 的 Build Type 包含构建、测试和重载选项，界面名称随版本可能不同：

- **Build & Test Your World**：重新构建并启动测试客户端。
- **Build & Reload Your World**：重新构建，交给已经启用世界监听的客户端重载。
- **Test / Reload Your Last Build**：复用上一份构建，不包含之后尚未构建的场景或脚本修改。
- **Clients / Number of Clients**：启动客户端数量；大于 1 可检查多客户端行为。
- **Force Non-VR**：以桌面模式启动。

先设两个客户端，交替操作并记录两端状态。多开会共享同一台机器的 CPU、GPU、内存和网络资源，其帧率不能直接当成单客户端性能结果。

Build & Test 使用真实 VRChat 客户端，但不能仅凭“同一台电脑”推断所有网络通信都是零延迟本地回环。真实远端用户、网络和平台仍需要单独测试。

客户端未启动时，依次检查客户端能否手动运行、SDK 设置中的路径、登录状态以及 Console 和客户端日志。若安全软件报告拦截，检查具体报告与文件来源，不把关闭防护或添加整个目录的排除规则作为通用排错步骤。

## 第四节：不同账号与 profile

需要验证账号隔离或权限时，用独立 profile 启动客户端，分别登录测试账号：

```bat title="vrchat_a.bat"
VRChat.exe --profile=1 --no-vr --watch-worlds
```

```bat title="vrchat_b.bat"
VRChat.exe --profile=2 --no-vr --watch-worlds
```

profile 区分客户端配置与登录状态；它不会自动创建账号。`--watch-worlds` 让手动启动的客户端参与本地世界重载。若使用 SDK 的 Build & Reload 流程，确认两个客户端进入了同一个测试实例。

公网测试中使用两个不同账号，并按实例加入条件进入同一实例。不要将 ClientSim 的模拟玩家、同账号本地测试与不同账号公网测试视为同一种证据。

## 第五节：上传版本的受限测试

世界首次上传默认是 Private；Friends、Invite、Group 等是实例访问类型，不是上传时世界可见性的四选一。

上传后从自己的世界列表或 SDK Content Manager 打开世界，再创建适合测试人员的受限访问实例，邀请测试者。Private 不表示资源只保留在本地，也不等于向所有持有链接的人保证保密。

测试顺序示例：

1. A 进入，记录初始状态。
2. A 改变共享状态，B 随后加入，核对当前状态。
3. A 与 B 同时操作同一对象，检查写入方和结果。
4. Owner 离开，剩余玩家继续操作。
5. 重生或重新加入，核对初始化与持久化恢复。
6. 创建新实例，确认哪些状态重置、哪些个人数据保留。

每个开关先写明本地或共享。个人镜子不同步可能正是预期；共享门不同步才是相应测试的失败。

## 第六节：Android / Quest

选择 Android 构建前，确认对应 Unity 编辑器已安装 Android Build Support。切换平台会重新导入资源；检查并保存项目改动。

两条测试路径：

- **上传 Android 构建**：保持同一个 World ID，上传后用独立运行的 Quest 或 Android 客户端进入测试实例。
- **Android Build & Test**：按官方移动设备流程配置 ADB、开发者模式和 USB 调试，通过 SDK 把本地构建传到已连接设备。USB 调试会授予电脑较强的设备操作能力，只对可信电脑启用，并按官方设备说明操作。

手机或平板可检查部分 Android 兼容性，但不能代替 Quest 头显的输入、视角和性能。通过 Link / Air Link 运行 PC VRChat 加载的是 PC 构建，也不能作为独立 Quest 构建的验证。

检查材质、贴图、Lightmap、后处理、视频与 UI。官方 Android 文档中的“头像只允许指定 Shader”等限制有明确适用范围；不能推导为所有世界材质会自动替换成 Standard Lite，或所有纹理强制降到 1K。

## 第七节：性能与可访问性

按目标设备的刷新率和项目预算记录帧时间、内存、人数与开启功能。没有适用于所有设备、所有世界的单一 FPS 上传门槛。

至少覆盖：入口、最复杂的视角、镜子开启、视频播放和计划人数。记录头像显示设置，以便区分世界负载与头像负载。

操作测试还应覆盖：

- 桌面与 VR 输入。
- 坐姿、不同 Avatar 身高和左 / 右手操作。
- 静音、字幕、界面语言与缺字。
- 关闭附加特效后的通路和关键反馈。

## 发布测试清单

- [ ] 记录本次世界、SDK 和客户端版本
- [ ] 本地交互与必要引用正确
- [ ] 构建包含本次修改，没有误用 Last Build
- [ ] 两个客户端验证共享与本地状态
- [ ] 后加入、Owner 离开、重生和重入有明确结果
- [ ] 上传版本的下载与进入流程通过
- [ ] 每个宣称支持的平台都在对应设备上测试
- [ ] 性能结果注明设备、人数、头像与效果设置
- [ ] 未测试的条件和已知问题单独列出

## 测试练习

把一个共享灯开关写成测试表：A 首先进并开灯，B 后加入，A 离开，B 关灯，再创建新实例。每一步记录两端预期与实际状态。对个人音量开关使用相同流程，比较其预期为何不同。

### 同一次交互在不同环境中的日志

在场景副本中建立[本地门调试示例](/surviving/debugging-mindset/#第二节在执行边界记录日志)，填好 `doorAnimator`，保留 `[Door]` 前缀。每轮从关门状态开始，只按一次；它没有同步代码，预期只改变操作者本机的门。

1. ClientSim 中按一次，在 Unity Console 记录入口、isOpen 和 SetBool 完成日志。
2. Build & Test 的客户端数设为 2，在 A 按一次，分别查 A、B 的画面与本次客户端日志；记录哪个进程产生了 `[Door]`。多开日志可按启动时间和该次操作标记区分，不把两个文件拼成一条执行链。
3. 按本章 profile 步骤登录两个测试账号，确认处在同一本地测试实例，重复操作，记录身份、配置与日志文件。
4. 再把同一测试版本上传为 Private 世界，由两个账号进入同一受限实例，重复一次。另列这次结果，不能把 profile 隔离本身当作公网测试。

只替换测试环境，不同时替换门脚本或同步方式。要比较共享门，再单独使用[同步门实现](/with-others/tell-everyone/#同步门的目标状态)，按同样步骤重测；预期与观察均单独记录。

### 可选引用缺失时的降级

使用[短效果广播的 ExplosionButton](/with-others/tell-everyone/#一次性网络事件)，在副本中先填好 `explosionSound` 和 `explosionEffect`，确认一次交互有声音与粒子。停止运行，只清空 `explosionSound` 引用，重新构建测试：预期仍收到交互并播放粒子，声音不播，也不出现这次缺少引用引起的 halted。查客户端日志确认，再恢复音源并重测。

这一脚本分别检查两个可选引用，因此缺少声音不会跳过粒子。若换成必需引用，应先写明“提示配置错误并停止该功能”等预期；不能把所有缺失都默默忽略。需要实际制造 Udon 停止的对照时，使用[受控故障实验](/surviving/debugging-mindset/#在副本中比较无保护与有保护)。
