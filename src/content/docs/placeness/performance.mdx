如果加上灯光、材质或交互后帧率下降，先记录变化前后的测试条件，再定位开销。不能仅根据世界类型、画面风格或 Draw Call 数判断性能。

## 确定测试条件

记录设备、分辨率、刷新率、图形设置、站位、可见玩家与头像、镜子和视频状态。每次对照只改变一项。

帧时间比单独看 FPS 更便于分配预算：`90 Hz` 对应约 `11.1 ms`，`72 Hz` 对应约 `13.9 ms`。这些是数学换算，不是 VRChat 对所有世界的统一合格线；目标由实际设备与运行模式决定。

VRChat 的 Avatar Performance Rank 用于头像，不能把世界写成官方的 Excellent / Good 等级。

## Stats：快速查看渲染统计

Unity Game 视图右上角的 `Stats` 显示当前编辑器画面的统计，例如：

```text
Batches                 145
Saved by batching        23
Tris                  234.7k
Verts                 312.4k
SetPass calls             89
Shadow casters            67
```

- `Batches`：实际渲染批次；同一个物体可能因多个材质、Pass、阴影或镜子产生多次绘制
- `SetPass calls`：设置 Shader Pass 等渲染状态的调用次数，不只是换 Shader 名称
- `Tris / Verts`：当前渲染的几何统计
- `Shadow casters`：投影相关物体统计
- `Saved by batching`：批处理节省的批次参考

这些数字提供线索，不能单凭最大的一项直接断定瓶颈。编辑器性能也不等于 VRChat 客户端性能。

## Profiler：定位具体耗时

打开 `Window → Analysis → Profiler`，运行场景或 ClientSim，记录相同路线的若干帧。

1. 在 CPU Usage 中查看 Scripts、Physics、Rendering、Animation 等耗时。
2. 选择异常帧，查看 Timeline 和调用层级。
3. 在支持的采样环境中查看 GPU Usage，区分 CPU 与 GPU 限制。
4. 检查 Memory 中纹理、Mesh、Audio 与分配变化。

编辑器可用于比较代码和资源变化，但不能假定 Unity Profiler 能像连接自己的 Development Build 一样直接连接发行版 VRChat 客户端。客户端实测使用其可用的性能显示和调试工具，并记录实际设备结果。

| 测量现象 | 可检查的原因 |
| :--- | :--- |
| CPU Rendering 较高 | 批次、材质状态切换、额外摄像机 |
| Scripts 较高 | 每帧循环、重复查找、字符串构造 |
| Physics 较高 | 活跃 Rigidbody、碰撞网格、接触数量 |
| GPU 耗时较高 | Shader、分辨率、透明覆盖、阴影、镜子 |
| 间歇性内存分配与卡顿 | 临时对象、资源加载、垃圾回收 |

## 批处理与 GPU Instancing

### Static Batching

固定物体在满足材质、Shader 和顶点布局等条件时，可以参与静态批处理。在 `Edit → Project Settings → Player → Other Settings → Rendering` 检查 Static Batching，再检查对象的 `Batching Static`，用 Frame Debugger 或 Stats 验证实际批次。

勾选 `Contribute GI` 不等于勾选 Batching Static。静态批处理也不保证「全部同材质物体只需一次 Draw Call」；可见性、Pass 和内部批次限制都会影响结果。

### Dynamic Batching

小网格在满足顶点属性、材质与变换等条件时可动态合批，但准备数据也有 CPU 开销。是否启用和是否有收益需通过对照测量，不能只按一个固定顶点数判断。

### GPU Instancing

重复的 Mesh 和兼容材质可使用 GPU Instancing。勾选材质中的 `Enable GPU Instancing` 后，检查实际是否实例化，以及与静态批处理、光照数据和材质属性的关系。

例如复制一组相同栏杆，记录开启前后的 Batches 和帧时间。开启选项是允许使用实例化，不是保证全部栏杆只绘制一次。

### 材质与网格

多材质槽通常增加子网格和绘制。可以合并重复材质、制作图集，但过度合并整片场景可能降低剔除粒度，并增加编辑成本。AssetBundle 是资源打包机制，不会自动替作者合并材质。

## Occlusion Culling

遮挡剔除可以排除被墙等物体遮住的渲染对象。适合有实际遮挡结构的场景；开放场地是否受益需测量。

1. 将固定大型遮挡物设置为 `Occluder Static`，需要参与静态剔除的对象设置为 `Occludee Static`。
2. 打开 `Window → Rendering → Occlusion Culling`。
3. 检查烘焙参数与可活动区域，执行 Bake。
4. 用 Visualization 检查门口、窗边、拐角和镜子附近。
5. 修改主要遮挡结构后重新烘焙。

透明表面不能直接当作实心遮挡。烘焙数据有内存成本，不是所有场景都必须靠它优化。

## 镜子与视频播放器

镜子需要额外渲染反射画面，开销受可见对象、分辨率、灯光和 VR 双眼处理影响，不能固定说成帧耗时恰好翻倍。

- 镜子默认关闭，并提供本地开关
- 按用途选择 Reflect Layers；只需要头像时检查 Player 与 MirrorReflection，后者用于镜中的本地玩家
- 限制分辨率，分别检查清晰度和耗时
- 评估 `Disable Pixel Lights` 对画面和性能的影响
- 同时启用多面镜子时重新测量

视频播放器包含网络下载、解码、纹理更新与显示的成本，与镜子不是同一种渲染流程。测试目标设备支持的播放器、分辨率和同时播放数量，提供停止或静音方式。

## 透明、阴影与画面覆盖

半透明表面需要混合，重叠覆盖会让同一像素被多次处理。粒子、玻璃和雾同时占据大面积画面时，需要检查 GPU 耗时。

- 不需要连续透明度的形状可评估 Alpha Clip，但它与半透明外观不同，也有成本
- 减少不可见或重复的透明层
- 降低覆盖屏幕的大粒子数量，检查近距离视角
- 对固定照明评估烘焙，关闭不必要的实时阴影
- 在移动设备上单独验证，不能按 PC 结果推断

不需要阴影的小物体可以关闭 Cast Shadows。实时灯数量本身不是完整预算：一盏大范围带阴影的灯也可能比多盏小范围无阴影灯更贵。

## Udon 脚本性能

Udon 的执行成本与原生 Unity C# 不同。按 [UdonSharp Performance Tips](https://creators.vrchat.com/worlds/udon/udonsharp/performance-tips/) 评估频繁执行的逻辑：

- 将固定组件引用缓存，或通过 Inspector 指定
- `GetComponent` 查当前物体的组件，`Find` 类 API 的查找范围不同，不能混写成所有调用都遍历整个场景
- 避免每帧构造不需要的新字符串或对象
- 大循环按实际数量与频率测量，必要时分批处理
- 只在交互时变化的状态使用事件；确实随时间变化的逻辑才持续更新

垃圾回收来自运行时的托管分配，不应称为 UdonSharp 自己有一套「更慢的 GC」。

## 按测量结果确定优化顺序

1. 固定测试条件，保存基线数据。
2. 找出占用较高且可以改变的一项。
3. 修改并重复同一路线，检查帧时间、内存和画面变化。
4. 保留有收益且符合功能要求的改动。
5. 在目标设备和计划人数下复测。

如果加入玩家后性能下降，还需区分世界开销和头像开销。使用可重复的头像组合，不能把全部下降都归因于世界。

## 对照练习

先另存测试场景，保持同一站位、相机朝向、分辨率和设备。等待资源加载结束，再取同一路线的一段稳定采样；记录通常帧时间和突增，而不是只抄某一帧的最高 FPS。每项改完先恢复基线，再做下一项。

| 实验 | 准备与唯一改动 | 记录与判断 |
| :--- | :--- | :--- |
| GPU Instancing | 新建一组相同 Sphere，使用同一份支持实例化的材质，放在同一视野内。为这组测试物取消 Batching Static，保持光照和数量不变，只切换材质的 Enable GPU Instancing | Game 视图 Stats 中的 Batches、SetPass 与帧时间；在 `Window → Analysis → Frame Debugger` 中选当前 Game 视图帧并启用检查，核对是否出现实例化绘制。没有减少时先查 Shader、材质实例、网格和其他合批条件，不推断勾选即生效 |
| 镜子反射层 | 按[镜子配置](/come-alive/sit-mirror-teleport/#反射层与分辨率)先准备一面可开关的镜子。保持镜子开启、分辨率及玩家头像组合不变，只把 Reflect Layers 从原设置改为所需 Player / MirrorReflection 等层 | 同一设备的帧时间、编辑器中可取得的渲染批次，以及墙面和头像是否按需求显示；不把「少画场景」误报成相同画面的无损优化 |
| 实时阴影 | 使用一盏 Realtime Light、同一组投影物，只将 Shadows 从原设置改为 None | 阴影消失的位置、目标辨认情况和可取得的 GPU / 帧时间；不同时关灯、缩 Range 或改灯数 |
| 遮挡剔除 | 在副本中记录未烘焙版本，再按本章标记并 Bake；出生点、门口、拐角、远景各保存一个相同观察位置 | Batches 与帧时间是否变化，物体是否错误消失。开放场地或视野内没有遮挡时，允许结果没有收益 |

最后在 VRChat 客户端用相同测试路线复测。编辑器中可用的 Frame Debugger 和 Profiler 不能据此当成发行版客户端的采样工具；没有某项数据时标为未取得。多人对照固定参与人数和头像，单独记录镜子状态，避免把头像变化算成世界优化收益。

## 性能检查清单

- [ ] 目标设备、刷新率、人数和测试路线有记录
- [ ] 编辑器数据与客户端实测分开记录
- [ ] 批处理和实例化的实际效果已验证
- [ ] 遮挡数据未造成物体错误消失
- [ ] 镜子、视频与大面积透明效果分别测过
- [ ] 脚本持续更新与临时分配有明确用途
- [ ] 多人及真实头像条件下完成复测
- [ ] 优化后重新检查交互和视觉功能
