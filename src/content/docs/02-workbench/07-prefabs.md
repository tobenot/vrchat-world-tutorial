## 先感受一下没有 Prefab 的绝望

你做了一个发光球。颜色调好了，Light 的 Range 范围调成 5，Intensity 强度调成 2。整体氛围看起来非常不错。

然后你希望在房间的另外三个角落里，各放置一个一模一样的发光球。你熟练地按下 `Ctrl+D` 复制出三个，用移动工具分别拖拽到指定的角落。房间里现在有了四个球。

半小时后，你越看越觉得 Range 5 太小了，灯光根本照不亮房间，应该统一改成 8。

于是你点击第一个球，修改参数；点击第二个球，修改参数；点击第三个球，修改参数；点击第四个球，修改参数。

四个球改起来似乎还算简单。

但现在，请在脑海里想象一下：你正在制作一条深邃的赛博朋克走廊，走廊两侧挂着二十盏壁灯。现在你希望稍微微调一下壁灯的霓虹颜色。二十盏灯，改二十次。当你修改到第十五盏灯的时候，你一定会开始抓狂并强烈地思考：**有没有一种办法，能让我只改动一次，所有同类型的灯光就跟着全部改变？**

答案是有。这就需要用到我们今天的主角 —— **Prefab（预制体）**。

## 制作一个场景物体的“模具”

Prefab 这个词，在中文开发语境里通常被称为「预制体」。你可以将它直观地理解为**「生产模具」**。你先在层级里精心组装、配置好一个物体，然后把它变成模具保存到项目硬盘中。以后想要用它，直接从模具里压出新的一份，就会是一个完全配置好的三维实体。

在 Unity 中的操作非常简单：

1. 在下方 Project（项目）面板的 Assets 目录下，新建一个专门存放预制体的文件夹，命名为 `Prefabs`（右键 → `Create` → `Folder`）。
2. 将左侧 Hierarchy 面板中已经配置好的 `GlowBall` 物体，**直接用鼠标拖入**到刚刚新建的 `Prefabs` 文件夹中。

拖拽完成的一瞬间，你会注意到两件非常神奇的变化：

* Project 面板的文件夹里，多出了一个蓝色的 `GlowBall.prefab` 文件实体。
* Hierarchy 面板中，那个 `GlowBall` 物体的名字和前面的小图标变成了显眼的**深蓝色**。

蓝色名字意味着：它现在已经光荣地晋升为了一个 **Prefab Instance**（预制体实例），和硬盘里的那个“模具”绑定了契约。

:::tip[为什么是这样？]
Prefab 的底层设计哲学是软件开发里极其经典的「单一数据源（Single Source of Truth）」和「不要重复自己（DRY - Don't Repeat Yourself）」原则。二十个灯的配置信息不需要复制二十份存在每一个角落，它只需要妥善储存在 `.prefab` 文件这一处即可。每个具体的灯光实例，只需要记录「我在世界的什么位置」以及「我跟模具有什么不同」即可。
:::

## 从模具中压出无限多的新实例

现在，你可以极其轻松地在 Project 面板中拖拽 `GlowBall.prefab` 预制体，将它直接甩进场景画面里。

你每拖拽一次，场景中就会多出一个完全配置好的发光球实例。我们拖拽三次，场景中就有了四个一模一样的发光球（算上最开始的那一个）。

为了后续修改时不头疼，我们将这四个球的名字分别规范修改为：`GlowBall_A`、`GlowBall_B`、`GlowBall_C`、`GlowBall_D`。

## 修改模具，所有实例全网同步

现在，我们来解决刚才修改二十次参数的绝望痛点。

双击 Project 面板里的 `GlowBall.prefab` 预制体文件。Unity 界面会发生变化，四周变暗，画面中央只留下这个单独的球，这代表你已经进入了 **Prefab 编辑模式**。

在这里，找到 Light 组件，把 Range 范围从 5 修改为 8。按下 `Ctrl+S` 保存，然后点击左上角的向左微型箭头，退出编辑模式。

回到你的场景中看一看。

你会发现场景里的四个发光球，其灯光照亮范围**全都自动变成了 8**。你仅仅修改了一次，所有的实例都在一瞬间完成了同步。这就是 Prefab 的最大威力：让同类物体的全局维护成本降为零。

## 允许个别实例展现“特立独行”的个性

有时候，你希望二十盏路灯在高度、大小上完全一致，但偏偏有且仅有一盏路灯需要闪烁着绿色的光芒。Prefab 允许你做这种局部的差异化。

在场景中，选中 `GlowBall_C`，去 Inspector 面板中将它的 Light 组件颜色直接修改为翠绿色。

修改完成后，你会注意到该字段旁边多出了一个小蓝条。点击选中的物体，在 Inspector 最右上方，会多出一个叫做 `Overrides`（覆盖）的下拉选项。这代表该实例在“颜色”这一属性上，和模具母体产生了不一致，这被称作 **Override**（覆盖参数）。

从此之后，如果你去修改模具的 Range 参数，`GlowBall_C` 的光照范围依然会跟随模具一起变大（因为你没有覆盖它的 Range）；但即使你把模具的灯光颜色改成了红色，`GlowBall_C` 依然会坚定地亮着它的翠绿色（因为它的颜色属性已经被你手动 Override 了）。

:::caution[踩坑预警]
Override 参数虽然极度灵活，但也容易引发混乱。如果你发现场景里某一个预制体实例身上的小蓝条多得连你自己都看不懂了，说明它的性质已经和模具产生了巨大的偏离。此时，请不要继续强行 Override，正确的做法是右键它并选择创建成一个全新的独立 Prefab，或者使用 Unity 提供的 Prefab Variant（预制体变体）来进行多级管理。
:::

## 什么时候应该把物体做成 Prefab？

一个极其简单的判断法则：**当你发现自己需要在场景里多次复制、配置同一组东西的时候，就是它该成为 Prefab 的时候。**

在 VRChat 世界里：

* 门需要做成 Prefab，因为每扇门都包含模型、碰撞体、音效和开关门脚本。
* 交互按钮需要做成 Prefab，因为点击逻辑可以全局复用。
* 甚至连椅子、篝火、灯泡、路牌、传送点等，一切具有重复性质的物件，都应该在诞生之初就做成 Prefab。

:::note[不同世界不同活法]
在搭建不同类型的 VRChat 世界时，Prefab 都是你维持项目不崩溃的根基。在温馨的「休闲世界」里，你可以把一盏精心烘焙过阴影的台灯做成 Prefab，然后在各种桌案上无限次摆放；在强逻辑的「游戏世界」里，你可以把一个复活点（Spawn Point）做成 Prefab，确保全图几十个出生点的参数和挂载逻辑完全对齐，避免因个别出生点配置漏掉导致玩家坠落报错。
:::

## Unpack Prefab：打破模具的羁绊

如果你在场景里放置了一个 Prefab 实例，但你想对它进行彻底的大改，彻底摆脱模具对它的控制。你可以右键该实例，选择 `Unpack Prefab`（解包预制体）。

解包完成后，它的名字会由蓝色重新变回普通的**黑色**。此后，无论你再去怎么修改 `.prefab` 文件，场景中的这个物体都不会再受到任何干扰。这非常适合当你引入了别人做好的优秀预制体资源、但需要拆碎研究其层级结构时使用。

:::caution[踩坑预警]
在正式项目开发中，使用 `Unpack` 必须要极其谨慎。一旦你解包了某样物体，它就彻底失去了全局一键更新的能力。如果后续由于 SDK 升级，全图的同类物体需要统一更改一个组件字段，这个被你解包掉的物体就必须由你手动一个一个去翻出来改，极易造成遗漏。
:::

## 像整理桌面一样整理你的项目目录

随着项目的推进，你的 Project 面板中会塞满成百上千个资源文件。请在第一天就强迫自己建立起如丝般规整的 Assets 目录结构，不要给未来的自己挖坑：

```text
Assets/
├─ Scenes/       (存放场景文件)
├─ Prefabs/      (存放你的预制体，内部可以再细分 Lighting, Interactive 等子目录)
├─ Materials/    (存放所有材质球)
├─ Audio/        (存放所有 MP3, WAV 背景音乐和交互音效)
└─ Scripts/      (存放你编写的交互逻辑脚本)
```

---

本章我们彻底征服了 Unity 中极其核心的 Prefab（预制体）机制：

* Prefab 是模具，Instance 是从模具中压出来的蓝色实例。
* 修改模具文件，场景中所有未被覆盖的实例都会全局同步改动。
* Override 允许个别实例在特定参数上展现独特的个性，而 Unpack 则能彻底断开与模具的契约。
