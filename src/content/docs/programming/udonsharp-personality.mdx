第 10 章学的 C# 语法是标准的，能在任何 C# 项目里通用。但放进 VRChat 世界项目里，就会遇到一些奇怪现象：明明照着 C# 教程写的，编译报错；明明写法跟普通 Unity 项目一样，运行时行为不一样；明明只是一个简单的递增，最后数组里第一个槽位莫名其妙是空的。

这些不是读者的错，是 UdonSharp 自己的脾气。这一章把已知的脾气一条条摊开，写脚本时少一份惊吓。

## 为什么会有这些限制

[第 2 章](/getting-started/about-vrchat/)铺过沙箱的来历：VRChat 客户端要执行陌生人写的代码，必须把可调用的 API 限制在一个白名单上，否则任何一个公开世界里都可能藏着木马。

这个白名单叫 **Class Exposure Tree**。写下的 C# 不是直接编成 IL 跑在 .NET 运行时上，而是先被 UdonSharp 编译器翻译成 **Udon Assembly**（一种字节码），再交给 VRChat 自己写的 Udon 虚拟机执行。这条路上每多一道转换，就多一些「这段普通 C# 写不通」的原因。

理解这条流水线之后，下面三类限制就有头绪了：

```text
1. .NET / Unity 的某些 API 不在白名单 → 调不到
2. UdonSharp 编译器还没支持某些 C# 特性 → 编译报错
3. UdonSharp 编译器自己的 bug → 编译过了但运行结果不对
```

第 3 类最坑，写脚本看不出问题，跑起来才发现行为不对。下面分别拆。

## 第一类：白名单里没有的 API

VRChat 暴露的 API 大致是：`UnityEngine.*` 的常用部分（不是全部）、`VRC.*` 的世界 API、`System` 命名空间的少量基础类型。其余基本访问不到。

以下是写脚本时大概率会撞上的，按重要性排：

```text
不可用：System.IO.*       读写本地磁盘
不可用：System.Net.*       发起网络请求
不可用：System.Reflection 反射
不可用：System.Diagnostics.Process 启动外部程序
不可用：System.Threading   多线程、Task、async/await
不可用：System.Linq        LINQ 查询语法
受限：  System.Collections.Generic.List<T> 等部分泛型容器
```

文件、网络、外部进程访问不到，是沙箱的硬性边界。设计世界的逻辑时不要假设能读取本地文件、不要假设能调用外部 Web API。需要持久化数据用 VRChat 自己的 [Player Persistence API](https://creators.vrchat.com/worlds/udon/persistence/)（SDK 3.7.4 起），需要外部数据走 [VRCUrl + VRCStringDownloader](https://creators.vrchat.com/worlds/udon/string-loading/) 这套受限通道。

判断某个 API 能不能调最方便的方式：在 Unity 编辑器里开 Udon Graph，节点搜索框里搜一下完整名字。搜得到能用，搜不到不能用。或者写在 UdonSharp 脚本里编译一次，编译器会直接告诉哪一行调用不在白名单上。

:::tip[为什么是这样？]
白名单不是临时凑的。它的核心是「这个 API 调用会不会让陌生世界访问到玩家电脑上不该访问的东西」。文件 IO 直接被禁；反射能绕开静态白名单，所以反射也禁；多线程会让 VRChat 客户端难以保证沙箱完整性，所以异步并发体系全禁。

这些禁令不是 UdonSharp 团队懒，而是「不禁就不安全」。
:::

## 第二类：UdonSharp 编译器还没支持的 C# 特性

这些不是沙箱阻拦，是 UdonSharp 编译器自身能力的边界。常见的有：

```text
不支持：自定义泛型类（class Foo<T> { ... }）
不支持：自定义泛型方法（部分情况）
不支持：async / await
不支持：yield return（即不能写迭代器）
不支持：event 关键字
不支持：自定义 indexer（this[int i]）
不支持：自定义 operator overload（== + - 等）
不支持：自定义 struct 中包含引用类型字段时的某些用法
不支持：UdonSharpBehaviour 上写 static 方法
受限：  ref / out 参数（仅在部分场合可用）
受限：  switch 表达式（C# 8 的 switch e => 写法）
受限：  字符串内插 $"..." （早期版本不支持，目前已支持，但旧文档可能写不能用）
```

普通 C# 教程很爱用的 LINQ（`list.Where(x => x > 0).Select(x => x.Name)`）和 async（`await Task.Delay(1000)`）在 UdonSharp 里都用不了。前者是因为 LINQ 内部依赖大量泛型和委托，后者是因为整个并发体系被禁。

VRChat 世界要做「等一秒之后做某事」，常用的写法是 `SendCustomEventDelayedSeconds`：

```cs
SendCustomEventDelayedSeconds(nameof(OnTimerFinished), 1f);
```

这是 UdonSharpBehaviour 自己提供的方法，绕开了 .NET 的 Task / Coroutine 体系，在 Udon 虚拟机里实现「过 N 秒之后调你这个方法」。功能上等价于 Coroutine，写法不同。

:::caution[踩坑预警]
看到一篇普通 Unity 教程让你写 `IEnumerator MyCoroutine()` + `yield return new WaitForSeconds(1f)` + `StartCoroutine(MyCoroutine())`，**这套在 UdonSharp 里不能用**。不是写法不对，是 UdonSharp 不支持 `yield`。把它翻译成 `SendCustomEventDelayedSeconds` 才行。
:::

## 第三类：UdonSharp 编译器的已知 bug

最隐蔽的一类。代码看着没问题，编译过了，但运行结果跟预期不符。下面几条是社区反复踩过的，到本书写作时（SDK 3.10.x）仍然存在。

### 后缀自增在赋值表达式里行为异常

写 C# 经常见到这种写法：

```cs
int i = count++;
```

按标准 C# 语义，`count++` 是「先取 count 当前值，然后再把 count 加 1」。所以 `i` 应该等于自增**前**的值，count 自增之后比 i 大 1。

UdonSharp 在这里跟标准 C# 不一致。在很多场合 `int i = count++;` 的实际行为等同于 `int i = ++count;`，i 拿到的是自增**后**的值。

这听起来像小事，但它会导致一类非常隐蔽的 bug：往数组里写入时第一个槽位永远被跳过。

```cs
// 写法 1：触发 bug
int slot = decorations.decorCount++;
decorations.items[slot] = newItem;
// 实际执行后 slot 是 1（不是 0），items[0] 永远没被填上
```

修复方法：拆成两条独立语句。

```cs
// 写法 2：安全
int slot = decorations.decorCount;
decorations.items[slot] = newItem;
decorations.decorCount = slot + 1;
```

社区里实证过的触发模式：

```text
风险：int i = X++;                       含成员访问 obj.field++ 也算
风险：return X++;
风险：func(X++);
风险：if (X++ < n) { ... }
风险：arr[obj.field++] = val;
经验证安全：arr[localInt++] = val;        local 变量做 indexer 的同源场景
经验证安全：count++ 单独成句
经验证安全：for (int i = 0; i < n; i++) { ... } 循环控制变量
```

最稳的做法：能拆就拆，避免在赋值或表达式里读后缀自增的返回值。需要保留 `arr[localInt++]` 这种已经验证过的写法时，写一行注释说明这里被刻意保留，方便后人维护。

:::caution[踩坑预警]
这条 bug 真实出现过。一个名为 VoidScavengers 的 VRChat 项目里，前后两次因为同一类 bug 卡过：第一次是楼层走廊数组里出现「幽灵走廊」（slot 0 没填，渲染出空气墙），第二次是装饰物 spawn 时把宝箱钥匙放进了史莱姆房间。每次都查了几个小时，最后追到这条编译器行为。

后来这个项目在 Editor 里加了一份静态检查脚本，每次脚本编译完成自动扫一遍，命中高危模式就直接 LogError，把这类问题挡在写代码这一步。在自己项目里如果反复栽跟头，可以参考这种思路加一个 lint。
:::

### 纯静态类必须放在 Plugins/ 文件夹

只装常量、不继承 UdonSharpBehaviour 的纯 C# 类，比如：

```cs
public static class WorldConstants
{
    public const float DefaultWalkSpeed = 2f;
    public const int MaxPlayers = 32;
}
```

这种类如果直接放在 `Assets/Scripts/` 这类普通目录下，UdonSharp 编译器会报错：

```text
Script without UdonSharpBehaviour definition should not have an associated UdonSharpProgramAsset
```

解决办法是把这个文件移到 `Assets/Plugins/` 目录下。Plugins 是 Unity 的特殊目录，里面的脚本走另一条编译路径，UdonSharp 不会要求它必须是 UdonSharpBehaviour。这些类仍然可以被 UdonSharp 脚本正常引用、正常用 `WorldConstants.MaxPlayers` 取常量。

:::tip[为什么是这样？]
UdonSharp 的工作流程是：扫描所有非 Plugins 区域的 C# 文件，把每个看作一个「待编译为 Udon 程序」的候选，然后给它配套一个 ProgramAsset。但纯静态类没有实例、不需要 ProgramAsset，配上之后变成一个空壳 Asset，编译器就抗议了。

把这类文件挪到 Plugins，等于告诉 Unity「这是普通 C# 库代码，不要走 UdonSharp 编译流水线」，问题解决。
:::

### UdonSharpBehaviour 上的 static 方法不可用

UdonSharp 不支持在 UdonSharpBehaviour 子类里写 static 方法：

```cs
public class Helper : UdonSharpBehaviour
{
    // 编译过不去
    public static int Add(int a, int b) => a + b;
}
```

如果确实需要工具方法，两条路：

- 把这些方法做成普通实例方法，通过场景里的某个 GameObject 上挂的脚本去调用。
- 把这些方法挪到 `Assets/Plugins/` 下的纯静态类里（不继承 UdonSharpBehaviour）。

### 运行时不能 AddComponent UdonSharpBehaviour

普通 Unity 项目里写 `gameObject.AddComponent<MyBehaviour>()` 是常规做法。UdonSharp 项目里这条路在运行时走不通：UdonSharp 的脚本被打包成 Udon 程序资产，需要在编辑期就跟 GameObject 绑定好，运行时新加挂不上去。

要做「按需出现的物体」的常见做法是：场景里预先放一个挂好脚本的物体，禁用着；用 `SetActive(true)` 启用即可。

## 一些惯用法上的小差别

除了上面三大类，还有一组细节差别，写脚本一两次就习惯了：

```cs
// 1. 初始化用 Start，不用 Awake。
//    UdonSharp 不保证 Awake 的执行时机跟普通 MonoBehaviour 一致，统一用 Start。
public override void Start() { ... }

// 2. 父类方法用 override，包括 Update / Interact / OnPlayerJoined 等。
//    标准 C# 里 Update 不需要 override，UdonSharp 里通常要写 override。
public override void Update() { ... }

// 3. Inspector 上看见的 public 字段都会被序列化到场景里。
//    不希望被外部修改的字段用 [SerializeField] private 替代。
[SerializeField] private float speed = 2f;

// 4. 跨脚本调用别的 UdonSharpBehaviour 上的方法，
//    用 SendCustomEvent("方法名") 或者直接拿到引用调方法。
//    SendCustomEvent 用字符串名字，写错了运行时才会报错。
otherBehaviour.SendCustomEvent(nameof(OtherBehaviour.DoSomething));
```

这几条不是 bug，是约定。看到老的代码风格不一样很正常，这本书里统一用上面这套。

## 一份排坑顺序

写脚本时撞墙了，按下面顺序排查能省不少时间：

```text
1. 看 Console 里有没有红字。
   报错有：先按报错信息修。多数报错说人话。
   报错没：进 2。

2. 看脚本是否真的挂在了想要它执行的 GameObject 上。
   GameObject 名字对、脚本拖错位置，都是常见的。

3. 看 Inspector 里每个引用槽是否真的指向了目标物体。
   槽位是 None 时调用会 NullReferenceException。

4. 看用到的 API 是否在白名单。
   Udon Graph 节点搜索框搜得到才能用，搜不到换写法。

5. 看是否撞上 UdonSharp 的特性限制（async/yield/泛型/static/...）。
   撞上了换 SendCustomEventDelayedSeconds 等替代写法。

6. 看是否触发了已知 bug（postfix++ 是头号嫌疑）。
   把 X++ 拆成两行，多数怪行为会消失。

7. 都不是的话，加 Debug.Log 把变量值打出来。
   `Debug.Log("到这了，值是 " + score);`
```

第 39 章会再展开一节关于调试的方法，那一节会专门讲怎么读 Console、怎么用 Debug.Log 拆问题。

## 这一章在脑子里留下来什么

第 9 到 11 章铺完之后，应该能拿到的：

- 知道程序是按顺序执行的指令、由变量、判断、循环、函数、类组合而成。
- 能看懂一段 UdonSharp 脚本：哪里是字段、哪里是方法、哪里在调用别的物体、什么时候会被执行。
- 知道 UdonSharp 不是普通 C#，遇到「怎么不行」时大致能猜到方向。
- 撞上 bug 时不慌，知道按上面那份顺序排查。

这一章里那份「白名单 / 编译器限制 / 已知 bug」三类清单不需要背。撞上具体怪现象时知道大概去哪一类里翻，比记住每条都重要。
