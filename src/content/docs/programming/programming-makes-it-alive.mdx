按本书已经完成的搭建步骤，场景包含地板、两面侧墙、灯球、基础材质和方向光，能用 `Build & Test` 进入。这仍是一间基础毛坯房，没有完整陈设。

本部的语法和执行链说明没有把音乐、雨声、桌椅或咖啡角自动添加到场景中。阅读一个代码例子，也不等于已经创建、挂载并测试了对应功能。场景完成状态应以 Hierarchy、组件配置和实际测试为准。

## 空间本身可以完成使用目标

如果目标是观景、展示或聊天，布局、视觉、声音和运行稳定性可以构成主要工作。一个没有复杂自定义脚本的世界，也可以具备完整体验并受到玩家欢迎。

增加交互同样不能保证有人使用。只有需求包含操作和状态变化时，才需要判断用已有组件、动画还是脚本实现。功能数量与受欢迎程度之间不能直接画等号。

## 脚本解决明确的状态变化

以本部的灯光代码为例，需求是「发生交互时翻转目标灯的启用状态」。它可以拆成：

- 事件：`Interact()`
- 目标：Inspector 中引用的 Light
- 变化：读取 `enabled`，取反并写回
- 验证：交互一次改变状态，第二次恢复

脚本不会因此修改房间布局、补上陈设或改善材质。空间制作和行为编写处理的是不同需求，也可以分别测试。

## 官方组件与 Udon 分别检查

出生点由 Scene Descriptor 配置，镜子、Pickup 和 Station 使用各自的 SDK 组件。它们不要求作者为每个基础功能编写 UdonSharp，也不能笼统解释成「背后都是 Udon 字节码」。

Udon Behaviour 承载自定义 Udon 程序；其他组件提供其文档中定义的功能。要增加额外行为时，先核对官方组件已有的字段和受支持事件，再确定需要什么自定义逻辑。

## 用实际状态决定工作项

当前房间可以按以下方式检查：

| 对象或功能 | 检查内容 |
| :--- | :--- |
| 地板和墙壁 | 位置、尺寸、碰撞是否符合当前布局 |
| 出生点 | 是否位于地板上方，朝向是否正确 |
| 材质与灯光 | 引用是否正确，目标表面是否得到预期照明 |
| 重复灯球 | Prefab 与实例覆盖是否符合配置要求 |
| 自定义脚本 | 是否实际挂载、引用是否有效、测试是否通过 |

没有明确需求的功能不必列为缺陷。已经列入需求却尚未创建或测试的内容，则保持未完成状态，不以章节阅读进度代替功能验收。
