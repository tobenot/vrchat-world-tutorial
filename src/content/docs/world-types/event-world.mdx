Event World 为演出、典礼、展会或聚会提供场地。它可以只用于一次活动，也可以作为可复用模板。两种情况都需要明确活动内容、计划人数、支持平台和操作人员。

## 可选方案：保留场地，更换每场内容

重复举办活动时，可以把舞台、看台、通路和控制面板作为固定部分，把背景、视频、海报及节目道具分成每场替换的内容组。先复制场景或建立版本记录，再更换内容；逐项检查面板引用、播放源、灯光预设、碰撞与许可证，最后按本场人数重新排练。复用模板不表示替换后的素材自动满足原性能预算。

单次活动可以使用专门的舞台与动线，仍需留出入退场和故障处理空间。是否做模板取决于计划复用哪些部分，不由活动类型或制作者经验决定。

| 可选活动形式 | 需要落到图上或节目表里的项目 |
| :--- | :--- |
| 演出 | 舞台、观看位置、节目音频与灯光控制 |
| 社群集会 | 集合区、分组区域、主持与讨论切换 |
| 典礼 | 发言或上台顺序、等候点、回到座位的路线 |
| 发布或展会 | 演示位置、各展位说明、演示中断后的替代内容 |
| 派对 | 主活动区、暂离聊天区、个人音量和可关闭效果 |

## 人数与实例安排

SDK 上传面板中的 Recommended Capacity 与 Maximum Capacity 分别控制推荐人数和最大人数。容量设置不会自动提供相应性能；需要在计划人数和目标设备上测试。

一场活动若超出单实例容量，可以安排多个实例。每个实例有自己的玩家和 Udon 网络状态；普通同步变量与网络事件不跨实例传播。

- 各实例独立举办时，为每个实例安排操作人员或自动流程。
- 共用直播源时，各客户端仍可能因网络和缓冲产生不同延迟。
- 需要协调开始时间时，另外设计时间基准和容错，不把“填写同一个 URL”当成精确同步。

记录每个实例的入口、访问类型、控制者和备用联系方式。世界不会保证把满场访客自动分配到符合活动计划的另一个实例。

## 舞台、看台与通路

用实际 Avatar 和玩家视角检查前排、后排、两侧及入口处的视线。角色身高、坐姿与其他头像可能改变遮挡情况，不应按单一默认身高推算全部座位。

后排需要补充画面时，可以增加相机与 RenderTexture 屏幕。它们会增加渲染开销，必须与舞台灯效、镜子和人数一起测量。传送观看点也是一种选项，但要清楚标明目的地，并保证落点没有碰撞问题。

可选的空间对照是抬高后排形成阶梯看台，或在舞台两侧加辅助屏幕。先用简单几何试搭，从坐姿、站姿和侧面检查遮挡与台阶通行，再决定是否保留；不能只依据空场截图选方案。前排可供持续观看，后侧留出不穿过观众视线的移动路线，两种位置都要能读取必要信息。

入场路线应能到达座位、个人设置和必要说明。离场或暂离区域不必经过舞台；留在场内聊天是否允许，由活动安排决定，不规定固定的散场时长。

荧光棒等 Pickup 是可选的表达道具，加入时检查复位、碰撞、声音和性能，不把它设为参与活动的必要条件。暂离聊天区与出口可以各有一路标；墙体不能代替语音测试。下载时间较长时，分别检查未用模型、贴图尺寸和 Shader，依据真实下载与帧时间记录减少负载，具体操作见[性能测量](/placeness/performance/)。

## 音频分工

把主节目、场内 BGM、环境声、互动反馈和玩家语音分别列出，确定它们何时播放、谁控制、是否按位置衰减。

- 需要全场不随距离变化的节目声，可使用 2D 音频；每位玩家仍可有不同的客户端或本地音量设置。
- 舞台音箱或环境声需要方向与距离感时，使用 3D 音频，并检查前后排的衰减。
- 区域进出控制播放的时机，Spatial Blend 控制空间化，两者分别配置。
- BGM 与节目切换时，检查是否重复播放或同时占用过高音量。
- 提供个人静音和音量控制，字幕或文字信息覆盖仅靠声音无法获取的内容。

例如按钮附近的确认音可用固定 3D 声源，主节目另用满足观看范围的音频方案。分别从按钮旁、前排、后排和暂离区试听，确认确认音不会被误当作全场节目，也不把空间化当作房间隔音。

## 视频播放器的边界

SDK 提供 `VRCAVProVideoPlayer` 与 `VRCUnityVideoPlayer`；带同步脚本的示例预制体负责实例内的播放状态。视频组件本身不自动规定操作权限或完整同步流程。

AVPro 支持官方列出的直播场景，但不能在 Unity 编辑器中验证实际播放，需要 `Build & Test`。Unity Video 的编辑器测试与客户端对托管网站 URL 的解析也不同。

检查项包括：

- 主源与备用源在目标平台是否可播放。
- 域名是否在官方允许列表；自托管源是否需要玩家允许不受信任 URL。
- 同时存在多个播放器时，URL 请求是否符合每位用户每五秒一次的限制。
- 后加入者、主持人离开、暂停和换源时是否恢复正确状态。
- 播放失败是否有文字提示及可操作的重试方式。
- 音乐、视频与直播内容的展示授权是否覆盖此次活动。

使用社区播放器时，另行核对其维护版本、许可证和控制权限，不能把某个预制体视为所有活动必需的组件。

## 灯效与个人控制

灯光方案分别记录基础照明和附加效果。激光、粒子和闪烁效果需要可关闭选项，关闭后仍应能辨认通路、舞台和文字。

不要用“低于某个频率”或“高于某个频率”保证闪光安全。闪光风险还受面积、亮度、对比等因素影响。可采用不闪烁的替代模式，并在进入相关区域前提供明确提示。

舞台灯控的权限与共享状态应有明确边界。操作者离开或脚本出错时，恢复到可看清通路的状态。

可选的节目亮度安排是：入场使用已测清楚的基础照明，节目段落逐渐调整舞台灯，结束恢复基础状态。每段分别记录基础光与附加效果；以无闪烁版本作为一种可选择的呈现方式。亮度变化也需要在目标设备上检查，不把“柔和”或“中等”当成安全保证。

## 按时段设计区域状态

以下是一个允许散场聊天的可选场地方案。它描述各区怎样运行，与排练时检查哪些故障是两张不同的表。

| 时段 | 舞台 | 观众区 | 暂离聊天区 |
| :--- | :--- | :--- | :--- |
| 入场 | 设备准备，节目未开始，背景显示说明 | 开放，基础灯光，个人设置可用 | 开放，指路清楚，单独试听音量 |
| 节目中 | 按节目表播放与切换灯光 | 保持通行与字幕可读，附加效果可关闭 | 保持开放，不必穿过舞台到达 |
| 结束 | 停止节目，恢复基础照明，显示结束信息 | 明确指向出口与聊天区两条路线 | 按主办安排继续开放，可选低音量 BGM |

把活动形式、人数、演出方式、是否复用和散场安排填在表前，再为每个格子注明控制者与状态来源。逐行演练切换，检查旧音轨、灯效或门状态是否残留。若不安排聊天，表中写明关闭或离场方案，不把上表当固定活动流程。

## 用活动时间表组织排练

| 阶段 | 检查内容 |
| :--- | :--- |
| 入场 | 下载、出生点、导览、座位、人数与帧时间 |
| 开场 | 控制权限、音视频源、必要说明 |
| 节目中 | 换源、灯效、个人音量、后加入者 |
| 中断 | 播放器错误、控制者离开、备用内容 |
| 结束 | 停止节目、恢复基础灯光、显示结束信息 |

排练记录设备、网络、人数、世界版本和失败步骤。多开客户端可检查一部分状态问题，不能代替真实参与者和目标设备的性能测试。

在活动日程中提前约定参与排练的人、所需设备与复测时间，给修复留下实际窗口。排练失败后明确由谁修、修后重跑哪一段，不以“彩排过一次”代替修复确认。

纪念品若用 PlayerData 保存，只能记录世界支持的数据或解锁状态；世界中的 Pickup 不会因被拿着就自动带到其他世界。

例如可以在本世界的纪念墙显示“已参加此场活动”的图案，把活动编号与解锁状态作为自己的数据设计，重新进入时恢复；若只做现场票根卡，则提供拿起和复位，不承诺离开世界仍能携带。两种方案都先写明数据范围与取得条件。
