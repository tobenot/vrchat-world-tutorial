Tool World 是用于完成具体任务的世界，例如 Avatar 灯光观察、材质参数演示、配色对照或声场测试。场景外观可以简洁，也可以有完整的美术设计；需要明确的是哪些元素属于测试条件，哪些属于装饰。

## 写明任务和限制

用可验证的动作描述功能，例如：“在三组灯光预设下观察当前 Avatar，并保存自己选择的背景颜色。”

同时注明不能完成的操作。世界里的 Udon 接口不等于 Unity 编辑器接口，不能仅凭一个按钮设计就承诺修改 Avatar 源文件、导出动画或编辑任意 Avatar 参数。功能实现以当前 SDK 暴露的 API 为准。

Unity 编辑器扩展在开发工程中运行，Tool World 在 VRChat 客户端中运行。只有需要实际客户端、玩家视角或多人观察的条件，才属于后者的测试范围。

### 按任务选择工具所在的位置

| 要完成的事 | 可选实现位置 | 需要验证的结果 |
| :--- | :--- | :--- |
| 批量整理工程资产、修改源文件 | Unity 编辑器工具 | 工程中的修改和导入结果 |
| 生成色板、比较数值或展示通用模型 | 网页或桌面工具 | 输出数据、文件格式与后续使用条件 |
| 观察当前 Avatar、头显视角或多人显示 | VRChat 工具世界 | 实际客户端和目标设备里的表现 |

可以组合这些步骤，但网页模型预览不代表 VRChat 渲染结果，编辑器工具也不能自动变成世界内功能。

可选的小型灯光观察间先包含纯色背景、几何参照物、一张有已知颜色值的测试色卡和一个固定观察位。色卡用于在同一设备与设置下对照，不声称它完成了显示器的专业校准。按任务增加全身观察、局部细节观察或截图取景位；若使用额外相机，记录开启数量并测量开销。

## 把操作流程落到界面

例如灯光观察间的流程：

1. 进入操作位，显示当前灯光、背景和镜子状态。
2. 选择预设，界面与场景同时更新。
3. 手动调整参数，显示当前数值和单位。
4. 保存个人设置，或恢复明确标注的默认值。

每个控件都要有标签、当前值和作用范围。“重置”应说明重置当前模块、全部本地设置，还是公共场景。

World Space UI 的文字大小按观看距离与目标设备验证，不能把 Canvas 的字号直接当成固定米数。按钮间距需要覆盖 VR 指针与桌面操作；重要状态同时用文字或图形表达，不只改变颜色。

### 四类控件各自显示什么

| 控件 | 当前状态 | 操作反馈 | 就地说明示例 |
| :--- | :--- | :--- | :--- |
| 按钮 | 可操作或不可操作 | 按下态后恢复，另显示操作结果；点击音可选 | “恢复本模块默认值” |
| Slider | 实时数值和单位 | 拖动时数值与目标参数一起更新 | “只改变本地灯光强度” |
| Toggle | “开 / 关”文字配位置或形状变化 | 切换后仍能识别当前值，不只换颜色 | “显示本地镜子” |
| Dropdown | 收起时显示当前选项 | 展开后当前项可辨，列表留出可点击间距 | “选择背景预设” |

把说明放在控件旁；需要更多文字时提供单独的详情入口。分别测试初始状态、操作后、不可用时与恢复默认值后，确认控件显示和实际场景一致。[按钮按下发光](/placeness/ui-and-feedback/)与[点击音](/placeness/sound-and-mood/)有现成的小例，World Space Canvas 和指针设置也在 UI 章节，不必另复制一套代码。

## 保持可复现的环境

测试结果应包含世界版本、平台、设备和预设。例如测 Avatar 表现时，记录光源种类、镜子是否开启、相机数量、背景和其他玩家是否显示。

不同平台可能使用不同构建和 Shader。PC 上的一个“Quest 预览”按钮不能等同在独立头显上运行 Android 客户端。

为了区分世界自身与待测对象的开销，可以准备基准状态：关闭附加模块、使用固定镜子设置、保持相同测试位置，再逐项开启对比。若工具就是用于测试实时光或复杂材质，则这些内容是测试负载的一部分，不应简单全部移除。

可选的基准场景只用简单墙地与几何块，采用目标平台支持的简单材质；不需要变化的照明可选烘焙，并停用与任务无关的粒子、额外音源和屏幕相机。先测这组状态，再一次增加一个模块；固定 Avatar、位置、镜子和其他玩家显示设置，保存前后记录。基准负载也要实测，不能仅用“简洁”判断开销。

其他可选实验包括：让滑条只改测试物体材质中实际存在的一个属性；并排展示原色、互补色和渐变；用同一按钮对照本地改变与共享改变；在固定位置对照某个效果开关前后的帧时间。每项只改变一个条件，并在界面写出条件与输出，避免把多个变化归因给一个参数。

## 预设与 PlayerData

把一组预设表示为一组参数：灯光强度和颜色、背景索引、镜子模式等。切换时一次应用整组值，避免界面显示的预设名与实际参数不一致。

例如“日光 / 夜间 / 办公室”是三组作者定义的灯光参数，不是对所有真实场所的精确模拟；背景可另选纯色、墙面纹理或色卡，用来分别检查轮廓、表面与颜色对比。预设记录中列出每组实际数值，镜头位置和可选模块开关也单独记录，不能只保存一个名称而遗漏场景状态。

需要跨次访问保留个人设置时，可使用 PlayerData：

- 在本地玩家的 `OnPlayerRestored` 之后读取数据。
- 为缺失键设置默认值，并限制读出值的有效范围。
- 只保存必要的个人偏好，不把购买权益或管理权限存成可自行改写的普通开关。
- 对连续拖动的 Slider，按需要在结束拖动或合适间隔保存，避免无意义地高频写入。
- 更改数据格式时保留版本字段和迁移逻辑。

PlayerData 以玩家和世界的数据范围保存，不会自动成为所有世界共用的设置库。无需保存的短时实验也可以在离开后重置，界面明确说明即可。

## 单人操作与多人演示

同一工具可以支持两种范围：

- 本地模式：每位玩家调整自己的显示，不影响旁人。
- 共享演示：指定控制者修改公共预设，其他玩家观看同步状态。

共享模式需要处理同时操作、控制者离开和后加入者。不能因工具以个人使用为主，就删去这些已提供多人功能的测试。

## 文档与验收

世界描述和操作位旁分别注明：功能、支持平台、必要条件、已知限制、版本和反馈方式。不要要求用户从控件名称猜测工具用途。

同时写明使用场景，例如“供需要比较同一 Avatar 在三组场景光照中表现的使用者”；这是任务条件，不是能力标签。把要做的动作限制成一份能验证的功能清单，再画 UI 草图：每个面板负责哪组参数、每个控件放在哪里、当前值和错误信息显示在哪里、怎样返回或恢复默认值。

可采用“自用非公开版本 → 请未参与制作的人按说明操作 → 修正标签、默认值与预设 → 满足发布检查”的迭代顺序。观察测试者能否不靠口头引导完成一项任务，记录找不到的控件和误解的作用范围，再复测同一任务。

测试表可包含：

- 初次进入是否有完整默认值。
- 每个预设是否应用了全部参数。
- 超出范围的保存数据是否安全回退。
- 保存后重新加入是否恢复正确。
- 两人同时操作是否符合标示范围。
- 关闭模块后是否释放了对应的额外渲染或音频负载。
- 没有音频、不同语言和坐姿条件下是否仍能完成操作。
