Game World 用规则规定玩家可以执行的动作和结果，例如跑酷计时、合作解谜、桌游或多人对战。游戏可以是单人本地逻辑，也可以让多个玩家共享状态；同步范围由玩法决定。

## 先写清规则和状态

以回合制小游戏为例，列出：

- 参与人数与开始条件。
- 玩家可以执行的动作，以及每个动作的合法条件。
- 分数、时间或目标完成度如何变化。
- 什么条件结束回合，平局如何处理。
- 玩家中途加入、离开或掉线时如何处理。
- 结束后清理哪些道具、重置哪些变量。

状态可以写成：`等待 → 准备 → 游戏中 → 结算 → 等待`。每条转换都要有触发条件和具体动作。[第 17 章的门状态](/come-alive/doors-and-states/)也是这种结构，只是管理的状态较少。

大厅与游戏区分离时，出生点放在大厅；规则、加入按钮和当前回合状态放在可见位置。等待者可以旁观或等待下一局，不必直接出生在进行中的比赛区域。

### 把原型缩成一个循环

可先把“多种职业、技能、道具和昼夜变化”搁置，只实现一个动作、一种计分方法和一条结束条件。以下是可选原型；每一项都要先写规则，不能只凭名称开始堆场景。

| 原型 | 动作与结束条件 | 最少要记录什么 |
| :--- | :--- | :--- |
| 踩格子 | 指定格子亮起，踏入合法格得分；完成约定轮数后结算 | 当前目标格、回合编号、有效得分与参与者 |
| 抢椅子 | 停止信号后占用空位；全部可用座位已分配后结算 | 当前阶段、座位占用、参赛名单；同时申请一座位时的裁决 |
| 合作推箱子 | 把一个箱子送到目标区即完成；掉出边界可复位 | 箱子状态、目标是否完成、复位请求与物体所有权 |

例如把第一行写成一句话：“每轮踩中指定格得一分，约定轮数结束后按总分结算。”先用少量格子验证一轮，再加轮次。可直接照做的另一个原型是[四按钮抢分小游戏](/with-others/multiplayer-mini-game/)，其中包含请求、Owner 裁决、比分显示和重置。

可选的空间流程是：大厅查看规则、选模式、加入并等待开始 → 进入游戏区 → 显示结算 → 返回大厅并允许重开。把开始、进入、结束、返回分别标到状态图上；若使用传送，检查落点和碰撞，操作方法见[传送点](/come-alive/sit-mirror-teleport/)。让没有参与制作的人走一次，分别测量“入场到能执行第一步”和“结算到能再开局”的时间，记录卡在什么说明或操作上，不设通用秒数要求。

## 共享数据由谁写入

每个客户端都运行自己的场景和 Udon 程序。若多个客户端独立改写同一比分，可能产生不同结果。

一种实现是给 GameManager 指定 Owner，由它处理动作请求并写入同步变量。发送请求的客户端不直接决定最终比分；Owner 检查当前回合、请求者资格和动作条件后再修改状态。

- 用 `Networking.IsOwner` 判断当前客户端是否有写入职责。
- 需要转移所有权时使用 `Networking.SetOwner`，并处理转移后的状态。
- 手动同步的字段变化后调用 `RequestSerialization()`。
- 接收端在 `OnDeserialization()` 根据已同步状态更新画面。

Owner 和 Instance Master 都是玩家客户端，不是可信的专用服务器。集中写入可以减少状态冲突，不能据此承诺防作弊。也不能把 Master 身份直接当作管理员权限。

例如进入终点 Trigger 只表示客户端提出“我到达了”的请求。Owner 仍检查请求者是否参赛、回合编号是否匹配、检查点是否满足规则，再决定是否结束回合；不能由到达者直接把“我赢了”写成所有人的结果。

调试时顺着同一条链定位：输入触发 → 请求送到当前 Owner → 资格与回合核验 → 修改状态 → 手动序列化 → 接收端更新显示。为每步记录回合编号和状态摘要；在场景副本中分别试有效请求、重复请求和上一回合的请求，观察应接受或拒绝的位置。具体日志入口见[调试](/surviving/debugging-mindset/)，多客户端步骤见[测试](/surviving/testing-your-world/)。这条链不要求每次点击都抢占 GameManager。

## 状态与事件各自记录什么

比分、当前阶段、回合编号和结束时间属于需要恢复的状态。按钮声、一次闪光等即时反馈可以由事件触发。

后加入者不会收到此前的网络事件重放。若开门只靠一次网络事件，后加入者可能仍看见关闭的门。把“门已打开”保存为同步状态，再由接收端重建显示，才能描述当前场景。

计时也要区分“本地开始倒数”与“以共享时间基准计算剩余时间”。每个客户端在接到消息时才开始相同长度的倒数，会受消息到达时间影响。

可把状态表分成三组：全局记录阶段、回合与结束条件；每位参赛者记录角色、资格与分数；每件道具记录位置、占用与复位状态。对每个字段再写明写入方和恢复方式。这三组是整理数据的方法，不表示必须各建一个同步对象。人数增加时，检查参赛槽位、计分板行数和更新量是否仍覆盖全部参赛者，不用仅增加一个人数常量替代这些检查。

## 中途加入和离开

设计两种明确路径之一：

- **允许加入当前回合**：同步角色、比分、地图状态和剩余时间，并安排合法的加入位置。
- **等待下一回合**：仍允许进入实例，但把玩家放在大厅或旁观区，不把其加入当前参赛名单。

世界中的游戏区限制与实例访问权限是不同系统。不能仅靠世界脚本中的一扇门，声称已经把实例关闭。

玩家离开时检查：是否需要移除其参赛状态、释放物体、重新计算结束条件，以及 Owner 转移后是否仍可继续计分。重置流程应能重复执行，不重复生成道具或累计错误分数。

## 交互与反馈

每次动作至少能检查三个结果：输入是否收到、动作是否获准、最终状态是什么。例如按钮被按下可以高亮，但高亮不等于已经成功加入比赛；还应显示“已加入”或具体失败原因。

计分板、时间和角色说明应在桌面与 VR 中可读。音效可以辅助反馈，但关键状态还需要文字、形状或图标，以覆盖静音和语言差异的情况。

可选反馈分工：按钮轻响表示输入已收到；计分文字变化表示裁决已接受；结算文字配结束音表示回合终止；警示音配原因文字表示动作不合法。分别静音测试，确认仅看界面也能区分这些结果。

物理道具需要分别验证本地运动与网络同步。`VRC Object Sync` 负责其支持的对象状态，同一游戏中的回合规则、归属和计分仍需要明确的脚本逻辑。

## 按玩法确定测试范围

| 玩法 | 需要记录的状态 | 重点测试 |
| :--- | :--- | :--- |
| 单人跑酷 | 本地检查点、开始时间、完成状态 | 重生、跳过检查点、重新开始 |
| 合作解谜 | 已完成目标、公共道具、门状态 | 两人同时操作、后加入、解题者离开 |
| 物理桌游 | 球或棋子的位置、轮到谁、计分 | 拾取竞争、物体复位、Owner 切换 |
| 对战 | 参赛者、回合、得分、结果 | 非法动作、平局、重复请求、离线 |

本地个人记录可以使用 PlayerData；它不会自动生成跨实例排行榜。若需要排行榜，必须另外说明数据范围、可用接口和可信度。

任务与投票玩法还需列出“领取任务、提交证据、投票、结算”的阶段条件，避免前一阶段的操作在后一阶段仍有效。移动平台和投掷物则要额外检查运动、拾取与所有权切换；它们可单独做测试场景，不必同时塞进首个回合原型。

## 做一份规则测试表

把“按下开始”“两人同时得分”“最后一名玩家退出”“结算后重开”等动作写成测试用例。每项记录操作前状态、操作顺序、各客户端预期状态和实际结果。

发布前至少验证完整回合、重复回合、中途加入和 Owner 离开。画面与交互的验收分别记录，避免把“能结束一局”误写成整个世界已经通过测试。
