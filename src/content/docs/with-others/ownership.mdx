第 26 章的两个客户端各自修改灯。对于需要共享的状态，必须确定哪个客户端负责写入并发布。VRChat 用对象的 Owner 管理这一点。

## Owner 的范围

网络化 GameObject 具有所有权。示例脚本使用自己所在的 `gameObject`，而不是任意拖入的普通 Light 物体。

- 初始网络对象默认由第一个进入实例的玩家拥有
- 所有权可以转移
- 只有 Owner 可以发布该对象的同步 Udon 变量
- Owner 离开时，VRChat 自动选择新 Owner

Owner 不是管理员身份。非 Owner 可以修改自己客户端里的普通字段或表现，但这种修改不会因此发布给别人。需要功能权限时，要另外设计权限条件。

实例 Master 与对象 Owner 也不同。不能依赖「新 Master 一定是最早加入的剩余玩家」，更不能用 Master 身份替代对象所有权检查。

## 打印当前 Owner

```cs title="LampToggle.cs"
using UdonSharp;
using UnityEngine;
using VRC.SDKBase;

public class LampToggle : UdonSharpBehaviour
{
    public Light targetLight;

    public override void Interact()
    {
        if (targetLight == null) return;
        targetLight.enabled = !targetLight.enabled;

        VRCPlayerApi local = Networking.LocalPlayer;
        VRCPlayerApi owner = Networking.GetOwner(gameObject);
        string localName = Utilities.IsValid(local) ? local.displayName : "unknown";
        string ownerName = Utilities.IsValid(owner) ? owner.displayName : "none";
        Debug.Log($"[Lamp] {localName}, enabled={targetLight.enabled}, " +
                  $"owner={ownerName}, IsOwner={Networking.IsOwner(gameObject)}");
    }
}
```

`GetOwner` 返回对象当前 Owner，`IsOwner(gameObject)` 判断本机玩家是否拥有它。

让 Alpha 先进入、Beta 后进入。两人分别按一次开关：日志中的 Owner 都可以是 Alpha，但本地灯都发生一次变化。这说明所有权不阻止本地代码执行。

`Light.enabled` 不能直接标记为 `[UdonSynced]`；需要共享开关状态时，应在 Udon 脚本中定义 bool，再将它应用到 Light。

## 交互时请求所有权

```cs title="LampToggle.cs（所有权测试版）"
using UdonSharp;
using UnityEngine;
using VRC.SDKBase;

public class LampToggle : UdonSharpBehaviour
{
    public Light targetLight;
    public bool ownershipLocked;

    public override void Interact()
    {
        if (targetLight == null) return;
        if (!Networking.IsOwner(gameObject))
            Networking.SetOwner(Networking.LocalPlayer, gameObject);

        // 请求未获准时，不继续执行依赖所有权的操作。
        if (!Networking.IsOwner(gameObject)) return;

        targetLight.enabled = !targetLight.enabled;
        Debug.Log($"[Lamp] owner={Networking.GetOwner(gameObject).displayName}, " +
                  $"enabled={targetLight.enabled}");
    }

    public override bool OnOwnershipRequest(VRCPlayerApi requester, VRCPlayerApi newOwner)
    {
        return !ownershipLocked;
    }

    public override void OnOwnershipTransferred(VRCPlayerApi newOwner)
    {
        if (!Utilities.IsValid(newOwner)) return;
        Debug.Log($"[Lamp] ownership transferred to {newOwner.displayName}");
    }
}
```

1. 把 `ownershipLocked` 保持为 false，保存并构建。
2. Alpha 按一次，记录 Owner。
3. Beta 按一次，确认转移后的 Owner 与两边日志。
4. Alpha 再按，重复检查。

这个版本仍只改变本地 Light。**SetOwner 转移的是负责发布状态的客户端，不自动同步组件属性，也不代替 RequestSerialization。**

本例用 `IsOwner` 避免重复请求，并在请求后检查结果。若玩法需要等待转移完成再继续，应在 `OnOwnershipTransferred` 中处理已记录的待执行动作，不能在未获得所有权时直接发布状态。

## 拒绝请求与转移回调

`OnOwnershipRequest` 返回 bool：true 允许请求，false 拒绝请求。两个参数分别是：

- `requester`：发起这次所有权请求的玩家
- `newOwner`：这次请求希望接管对象的玩家；请求者也可以为另一位玩家请求，因此两者不一定相同

请求方与当前 Owner 都会评估请求，因此判定依赖的数据应一致；不同客户端使用互相矛盾的本地条件，可能导致不一致行为。

测试拒绝时，在构建前将 `ownershipLocked` 设为 true，或使用明确的调试按钮改变它，再记录各端值。构建后的客户端不会自动读取你在 Unity Inspector 中新改的值。

拒绝转移不会自动取消已经进入的 `Interact` 方法，因此代码需要在拒绝后停止依赖 Owner 的修改。这个版本包含第二次 `IsOwner` 检查。

`OnOwnershipTransferred` 表示对象所有权已经变化，会通知实例中的各客户端；仅为更新各端的 Owner 显示，不必再广播一次 All 事件。它可用于更新 UI、重新检查临时状态或接管管理逻辑。不要无条件清空同步分数或回合；新 Owner 应继续使用已接收的状态。

## 可选例子：用共享比赛状态锁定接管

`ownershipLocked` 是各端独立的测试开关。若拒绝条件来自共享比赛状态，就要保存并发布该状态。本例是单独的所有权练习，使用[Manual 状态同步的四个部分](/with-others/tell-everyone/#manual-状态同步的四个部分)：当前 Owner 开始或结束比赛，其他玩家尝试接管。

```cs title="MatchOwnershipLock.cs"
using UdonSharp;
using UnityEngine;
using VRC.SDKBase;
using TMPro;

[UdonBehaviourSyncMode(BehaviourSyncMode.Manual)]
public class MatchOwnershipLock : UdonSharpBehaviour
{
    public TextMeshProUGUI statusText;
    [UdonSynced] private bool isInMatch;
    private bool ready;

    private void Start()
    {
        ShowState();
        if (Networking.IsOwner(gameObject)) _InitializeOwner();
    }

    public void _InitializeOwner()
    {
        if (!Networking.IsOwner(gameObject) || ready) return;
        if (!Networking.IsNetworkSettled)
        {
            SendCustomEventDelayedSeconds(nameof(_InitializeOwner), 0.5f);
            return;
        }
        ready = true;
        ShowState();
        RequestSerialization();
    }

    public override void Interact()
    {
        if (!ready) return;
        if (!Networking.IsOwner(gameObject))
            Networking.SetOwner(Networking.LocalPlayer, gameObject);
        if (!Networking.IsOwner(gameObject))
        {
            if (statusText != null) statusText.text = "未取得控制权，请等比赛结束后再试";
            return;
        }
        ShowState();
    }

    public void _SetMatch(bool running)
    {
        if (!ready || !Networking.IsOwner(gameObject)) return;
        isInMatch = running;
        ShowState();
        RequestSerialization();
    }

    public override bool OnOwnershipRequest(VRCPlayerApi requester, VRCPlayerApi newOwner)
    {
        return ready && !isInMatch;
    }

    public override void OnDeserialization()
    {
        ready = true;
        ShowState();
    }

    public override void OnOwnershipTransferred(VRCPlayerApi player)
    {
        if (Utilities.IsValid(player) && player.isLocal) _InitializeOwner();
        ShowState();
    }

    private void ShowState()
    {
        if (statusText == null) return;
        VRCPlayerApi owner = Networking.GetOwner(gameObject);
        string ownerName = Utilities.IsValid(owner) ? owner.displayName : "等待 Owner";
        statusText.text = !ready ? "同步中" :
            $"Owner: {ownerName}\n比赛中: {isInMatch}";
    }
}
```

开始和结束按钮只在本机调用同一个控制对象，由该对象再次检查本机是否为 Owner：

```cs title="MatchStateButton.cs"
using UdonSharp;
using UnityEngine;

[UdonBehaviourSyncMode(BehaviourSyncMode.None)]
public class MatchStateButton : UdonSharpBehaviour
{
    public MatchOwnershipLock match;
    public bool startMatch;

    public override void Interact()
    {
        if (match != null) match._SetMatch(startMatch);
    }
}
```

1. 创建名为 `MatchControl` 的 Cube，保留普通 Collider，挂 `MatchOwnershipLock`，确认 Manual。创建 World Space Canvas 与 TMP 文本，拖入 `Status Text`。
2. 再创建两个带 Collider 的 Cube，挂 `MatchStateButton`，`Match` 都引用 `MatchControl`；开始按钮勾 `Start Match`，结束按钮不勾。标注开始、结束和申请接管三种用途。
3. Alpha 先进入成为 Owner，Beta 后加入。等待双方显示同一个 Owner 和 `比赛中: False`。
4. Alpha 按开始。双方收到 true 后，Beta 按 `MatchControl`：Owner 不变，Beta 的面板给出未取得控制权提示。Beta 按开始或结束也不能发布状态。
5. Alpha 按结束，双方收到 false 后，Beta 再申请接管，确认 Owner 改为 Beta；Beta 此时可以开始比赛。
6. 比赛锁定时让 Owner 离开，检查自动接管后已有 `isInMatch` 保留，新 Owner 可按结束按钮解锁。

这类条件也可表达「道具已分配给某位玩家」或「宝箱的当前操作尚未结束」。主持人开关另需检查明确的玩法身份；对象 Owner 本身不代表主持人资格。共享字段传播期间两端可能暂时不同，因此锁定与解锁测试都先确认双方收到状态。这是交互规则，不是可信反作弊或数据保密边界，也不能阻止 VRChat 在 Owner 离开时自动分配新 Owner。

## Pickup 的所有权

配有 `VRC Pickup` 与 `VRC Object Sync` 的物体，在抓取时由抓取者接管并同步移动。可在[PickupGlow 的完整脚本与接线](/come-alive/pickup-and-throw/#第四步添加灯光反馈)所用脚本里增加以下回调；保留原有 OnPickup / OnDrop 亮度处理，并确认文件已有 `using VRC.SDKBase;`：

```cs
public override void OnOwnershipTransferred(VRCPlayerApi player)
{
    if (!Utilities.IsValid(player)) return;
    Debug.Log($"[Pickup] owner={player.displayName}");
}
```

两位玩家依次抓取并放下，逐项记录：谁触发本地 OnPickup → 两端转移回调报告谁为 Owner → 抓取者移动物体 → 另一端观察位置。Pickup 事件和 Object Sync 的位置同步是不同机制，不以远端是否出现同一条 OnPickup 日志作为唯一判断。

## 多人同时操作的条件

只有一个 Owner 不代表所有权转移自动解决全部竞争问题。两个人几乎同时请求所有权、基于旧值修改计分，仍可能覆盖对方状态。

两种设计可以按需求选择：

- 操作者接管对象：适合物体操控或不要求累计每次竞争操作的状态切换
- 保持管理对象的 Owner，由其他玩家发送请求给它：便于集中检查回合、计分和重复请求

后一种模式中的 Owner 是玩家客户端，不是可信的独立服务器。仍需处理网络延迟、离线和状态校验。

## Owner 离开时

1. 在多人实例中确认当前 Owner。
2. 让它离开，检查新 Owner 的回调。
3. 在剩余客户端继续交互，确认功能仍可用。
4. 检查临时锁、玩家列表与未完成操作。

已请求但尚未成功发送的本地变化可能无法被接手。重要状态需考虑发送结果与恢复，而不是假定每次 RequestSerialization 已立即到达所有人。

## 检查清单

- [ ] 所有权操作针对正确的网络化 GameObject
- [ ] 本地表现与同步数据的责任分开
- [ ] 请求被拒绝时不会继续执行依赖 Owner 的修改
- [ ] 两边日志确认相同 Owner
- [ ] 同时操作的竞争结果有明确规则
- [ ] Owner 离开后可以继续运行
