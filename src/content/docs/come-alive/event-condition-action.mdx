本部示例可以按三个部分检查：什么事件启动代码，什么条件允许继续，代码改变哪个对象。这个划分描述程序结构，不保证只写三段就能覆盖每种交互需求。

## 事件：代码从哪里开始执行

事件方法是 VRChat 或 Unity 在相应条件下调用的入口。例如：

```cs
public override void Interact() { ... }
public override void OnPlayerTriggerEnter(VRCPlayerApi player) { ... }
public override void OnPickup() { ... }
public override void OnStationEntered(VRCPlayerApi player) { ... }
```

这些是签名示意，省略号不能直接作为完整 C# 程序编译。

| 入口 | 条件与范围 |
| :--- | :--- |
| Interact | 本地玩家对可交互对象操作，需要命中 Collider 等条件 |
| OnPickup / OnDrop | 本地玩家拿起或放下 Pickup |
| OnPickupUseDown / Up | 本地玩家持有物体时按下／释放 Use，桌面模式需要 Auto Hold |
| OnPlayerTriggerEnter / Exit | 当前客户端检测到玩家胶囊体进入／离开区域，参数可能是本地或远端玩家 |
| OnStationEntered / Exited | 座位进出回调，通过 player 参数判断对应玩家 |
| Start / Update | 对象初始化／逐帧生命周期调用 |
| 延时自定义事件 | 由 SendCustomEventDelayedSeconds 等调用安排执行 |
| 其他脚本调用的方法 | 由调用方选择执行时机与目标 |

`OnPlayerTriggerEnter` 不是可靠网络广播。不同客户端看到的位置与检测时刻可以不同，瞬移和高速穿越还可能漏发。`Interact` 与 Pickup 的本地操作，也不会因为多人同处一个实例而自动执行在每个人的脚本上。

## 条件：这次调用是否执行动作

本部用到的条件包括：

```cs
if (!Utilities.IsValid(player) || !player.isLocal) return;
if (mirrorObject == null) return;
if (isAnimating) return;
```

| 条件 | 作用 | 不保证什么 |
| :--- | :--- | :--- |
| 玩家有效且 isLocal | 只处理本机玩家对应的事件 | 不同步状态，也不检查对象所有权 |
| 引用不为空 | 避免对未配置对象执行操作 | 不保证引用指向正确对象 |
| 动画锁未开启 | 限制重复操作 | 不自动检查动画是否完成 |

这些条件按需求使用。例如音乐区只为自己播放，因此过滤本地玩家；记录所有玩家的区域活动时，不能照抄这个过滤后还期待得到所有人的事件。

空引用保护会让本次方法提前返回，因此「Console 没报错」不等于功能已配置正确。仍要核对引用槽，并观察结果。

状态锁也有行为选择：忽略新请求、记录最新请求或按顺序排队，结果并不相同。第 17 章的按钮门采用忽略；需要玩家离开后自动关闭的门，必须考虑离开发生在开门动画中的情况。

## 动作：修改属性或调用方法

本部用到的动作是：

```text
属性修改     light.enabled / light.intensity / light.color
物体显隐     gameObject.SetActive(...)
播放控制     audio.Play() / audio.Stop()
动画参数     animator.SetBool("IsOpen", ...)
座位使用     Networking.LocalPlayer.UseAttachedStation()
位置变更     localPlayer.TeleportTo(...)
安排延时     SendCustomEventDelayedSeconds(...)
```

动作的影响范围由 API 和配置决定：

- 关闭 Light 组件不等于关闭网格或移除烘焙光照。
- `SetActive(false)` 会禁用物体及其活动子层级；镜子开关应放在该层级外。
- `Stop()` 后再 `Play()` 从头播放，与 `Pause()` / `UnPause()` 的暂停续播不同。
- Animator 参数代表输入给状态机的目标，不一定等于此刻门板的实际角度。
- `TeleportTo` 只能移动本地玩家，还受 Station 等条件限制。

同一动作被多个事件使用时，可以抽成独立方法。例如 `ApplyState()` 负责把状态映射到颜色或 Animator 参数，事件只修改状态并调用它。拆分依据是职责和复用，不能仅按代码长短判断。

## 对照本部示例

| 示例 | 事件 | 条件 | 动作 |
| :--- | :--- | :--- | :--- |
| 灯开关 | Interact | Light 引用有效 | 翻转 enabled |
| 区域 2D 音乐 | 玩家 Trigger Enter / Exit | 有效本地玩家、AudioSource 引用 | Play / Stop |
| 发光 Pickup | Pickup / Drop / Use | Light 与颜色数组有效 | 改强度或颜色 |
| 座椅 | Interact | 本地玩家有效、Station 配置完整 | UseAttachedStation |
| 镜子 | Interact | 镜子根物体引用有效 | SetActive |
| 区域传送 | 玩家 Trigger Enter | 有效本地玩家、终点引用 | TeleportTo |
| 旋转门 | Interact | Animator 引用、动画锁 | 翻转目标状态、SetBool、延时解锁 |

例如「踩入台阶区域让台阶变色」，需要区域事件、玩家范围判断、Renderer 引用以及恢复颜色的离开路径。再加上「只有拿着钥匙才变色」，就是额外读取钥匙状态的条件。

## 初始化和恢复也是程序的一部分

只检查事件中的动作还不够。以下问题决定连续使用是否正确：

1. **开始是什么状态？** 区域音乐的 Play On Awake 关闭，门的 bool 与 Animator 默认状态一致，信号灯 Start 应用第一种颜色。
2. **再次触发会怎样？** 音乐播放中不重复 Play，按钮开关能反复切换，动画锁有明确释放条件。
3. **怎样恢复？** 离区停止音乐、掉落物复位、退出座位恢复灯光。
4. **异常路径是否覆盖？** 出生在区域内、瞬移、禁用对象、玩家离开等，不一定等同正常 Enter/Exit。
5. **谁能看见变化？** 本地 UI、音乐和公共门的共享状态需求不同，不能用同一种同步假设。

## 多个交互共享状态

考虑「三把不同钥匙都被取得，门才打开」。每把钥匙可以是 Pickup，但门需要知道整体收集状态。

一种实现方式是增加协调脚本，保存三把钥匙是否已取得。每把钥匙通过引用调用协调脚本中对应的公开方法，协调脚本检查三个状态，再更新门的 Animator：

```text
钥匙 A 的 OnPickup → 标记 A 已取得
钥匙 B 的 OnPickup → 标记 B 已取得
钥匙 C 的 OnPickup → 标记 C 已取得
                         ↓
                    检查 A、B、C
                         ↓
                    设置门的目标状态
```

用独立标记而不只是每次 Pickup 都 `count++`，可避免反复拿同一把钥匙被算作多把。还需明确放下是否撤销收集、重置时如何清空，以及状态属于每个人还是所有人共享。

各对象仍有事件、条件、动作，但共享状态需要明确负责人。引用或 `SendCustomEvent` 提供调用方式，本身不解决这些规则。

## 检查清单

- 事件名字、签名、组件与触发条件是否匹配？
- 玩家范围、空引用、重复触发条件是否符合需求？
- 动作实际改了哪个对象、哪个属性？
- 初始状态、恢复路径与多客户端结果是否经过测试？
