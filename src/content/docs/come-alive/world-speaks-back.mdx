本部示例给房间添加按钮、音乐区域、可抓取物体、座椅、镜子、传送与门。项目中实际存在哪些功能，以已经完成并测试的对象为准；读过章节不等于场景已配置好全部组件。

静态场景可以提供观景、展览或交流空间，交互用于满足具体操作需求。增加机关不自动提高质量，也不保证有人使用。判断依据是功能是否服务场景用途，以及玩家能否识别和完成操作。

## 把需求写成可检查的行为

以一个尚在搭建的咖啡厅为例，可把需求记录为：

| 需求 | 对象与连接 | 检查结果 |
| :--- | :--- | :--- |
| 允许玩家开关自己的灯 | 按钮 Collider、Interact、Light 引用 | 连续两次操作分别关闭与开启 |
| 跨过室内边界开始背景音乐 | 覆盖室内的 Trigger、本地玩家过滤、2D AudioSource | 区外不播，区内移动不产生距离或方向变化 |
| 杯子能被拿起 | Collider、Rigidbody、VRC Pickup | 桌面与 VR 可拿起、使用、放下 |
| 沙发可坐 | Station、交互脚本、EnterPoint、ExitPoint | 可以坐下与退出，位置和姿态可用 |
| 按需照镜子 | SDK 镜面 Prefab、独立开关 | 默认关闭，开关可用，能看见本地及远端 Avatar |
| 门允许通过 | 有实际门洞的墙、旋转门板、Animator、按钮 | 动画后门洞无残留阻挡 |

表中的对象不是对场景已有内容的描述。如果尚无杯子、沙发或吧台模型，可使用明确标注的占位几何体，分别验证功能与尺寸。

## 音乐的需求不能混写

「走进咖啡厅开始 BGM」与「吧台收音机一直在响」是两种需求。

- 本部音乐区示例使用本地触发的 2D 音乐。脚本控制播放时机，声音不随区域内的位置改变方向与距离音量。
- 固定收音机可使用独立持续播放的 3D AudioSource。玩家移动后改变的是与这个固定声源的相对方向和距离，室外也可能听到。
- 一进入世界就播放的全局 2D BGM 不需要区域 Trigger。

墙体不因有 Collider 就隔音，Spatial Blend 也不负责判断室内外。需要隔墙变闷、离区静音或淡入淡出时，应把对应规则单独列出，不能视为 3D 音频自动完成的结果。

## 明确本地与共享范围

本部的灯开关、音乐区、镜子按钮与门脚本，直接改的是当前客户端的对象状态。Pickup 的灯光反馈同样只在执行事件的客户端改变。场景中没有明确同步的字段或组件，就不能假定所有人看到相同结果。

本地行为本身有用途：每个人可按需打开自己的镜子，音乐也可只对进入区域的人播放。公共门或公共游戏状态则需要共享一致性，包括当前状态、写入方、同时操作和新加入玩家的初始化。

SDK 组件也各有职责。Station 的坐姿系统、Object Sync 的物理同步、Udon 脚本中的自定义颜色不是同一层功能；添加一个同步组件不会自动共享全部脚本字段。

## 操作反馈与退出路径

一个功能的可用性包含入口、反馈和恢复：

- 按钮提示说明动作，双语或图标帮助目标受众理解；自定义 Interaction Text 不自动翻译。
- 灯光或颜色变化应让操作结果可辨认，材质自亮与实际照明需分开观察。
- 座位应有可用退出方式，镜子关闭后开关仍可访问。
- Pickup 放下或掉出范围后仍有合理处理；传送点避免循环触发。
- 动画锁的等待时间与实际运动一致，重复输入不会留下未处理的状态。

这些条件可以逐项复测，不依赖玩家是否觉得新奇。

## 记录已验证与未验证的部分

单人 Build & Test 可验证本机操作，不能证明多人一致性或所有设备兼容。检查记录可以按以下格式填写：

```text
对象：MusicZone
配置：单个 Box Trigger；本地过滤；2D 音频
已测试：从区域外步行进入、离开、再次进入
预期：进入播放、离开停止、重新进入从头播放
未测试：区域内出生、瞬移进出、双客户端
```

对 Pickup 记录组件版本和 Auto Hold；对握持锚点记录桌面、VR 左右手的测试；对镜子记录目标平台、反射层和开启后的性能。配置改变后，原结果只说明原配置，不自动适用于新版本。

## 交互数量与场景用途

如果房间只需要静态展品和背景音，就不必为了覆盖组件种类而增加门、座椅或抓取。若展品需要旋转查看，Pickup 或旋转按钮才有明确用途；若空间需要位置跳转，传送才解决实际动线问题。

可用需求表逐项判断保留哪些功能：目的是什么，操作在哪发生，结果影响谁，怎样恢复，已经验证哪些条件。它既适用于只有一个按钮的场景，也适用于包含多个关联状态的交互。
