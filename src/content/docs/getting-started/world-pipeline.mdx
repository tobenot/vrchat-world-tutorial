[第一个世界](/getting-started/first-world/)用 `Build & Test` 加载了本机制作的场景。构建、加载和加入实例是不同环节；它们的错误需要分别检查。

## 场景保存的是对象和资源引用

`.unity` 场景文件记录 GameObject、组件、层级和可序列化字段。使用文本序列化时，它采用 YAML 格式。以下是示意结构，不是实际文件语法：

```text
Floor
  Transform：位置 0,0,0；缩放 10,0.2,10
  Mesh Filter → Cube 网格
  Mesh Renderer → 地板材质
  Box Collider → 碰撞形状
Spawn
  Transform：位置 0,0.2,0
WorldDescriptor
  VRC Scene Descriptor：Spawns[0] → Spawn
```

网格、材质、贴图、音频和程序资产可以是场景之外的资源。场景保存对它们的引用，不需要把每份原始文件直接写进场景文本。因此，移动或复制工程时必须保留资源与对应的 `.meta` 信息，不能只复制 `.unity` 文件。

## 构建：把资源转换成客户端可加载的形式

SDK 先检查场景要求，再调用 Unity 的构建工具。过程包括：

1. **收集依赖**：从场景及构建配置找出所需的模型、材质、贴图、音频和程序等资源。
2. **准备目标平台资源**：按平台处理贴图、Shader 等内容，并编译所需的 Udon 程序。
3. **生成世界包**：构建客户端可加载的 AssetBundle；本地 VRChat 世界构建文件通常使用 `.vrcw` 扩展名。

把一个文件放进 `Assets` 不等于一定会打进世界包；是否包含还取决于引用、特殊资源目录和构建流程。检查包体时应查看实际依赖，不能只按工程目录总大小判断。

这里构建的是供已有 VRChat 客户端加载的内容，不是把整个 Unity 工程变成一个新的独立游戏程序。原始 PSD、编辑器工具和源码也不等于它们的运行时资源形式。

## Build & Test：本机加载

`Build & Test` 生成本地构建结果，并启动 VRChat 加载它。SDK 的 Builder 设置可以指定客户端数量及是否强制桌面模式。`Build & Reload` 则用于把运行中的客户端切到新构建结果，具体选项以当前 SDK 面板为准。

这一步不会上传或公开世界，其他人的普通客户端不能通过世界目录找到这份本地构建。官方工具允许在同一电脑上启动多个测试客户端，用来观察支持的多人行为；因此「本地测试」不等于所有网络能力都被关闭。参见 [Build & Test 文档](https://creators.vrchat.com/worlds/udon/using-build-test/)。

如果构建完成但客户端没有启动，检查 SDK 中的 VRChat Client 路径、客户端数量和启动日志。如果客户端启动后场景不对，确认当前打开并保存的是预期场景。

## 上传：保存世界资源和描述信息

`Build & Publish` 使用账号授权把构建结果和世界信息上传到 VRChat。世界名、描述、缩略图、容量、标签和访问状态等是世界记录的一部分，不应全部当作 AssetBundle 内部字段。

世界拥有形如 `wrld_...` 的 ID。更新同一个世界时，关联的是新的资源版本；它与「重新创建一个新世界 ID」不同。VRChat 通过自己的内容分发服务向客户端提供资源，无需在教程中假定具体存储供应商或 HTTP 请求实现。

上传成功也不等于所有玩家都能搜索和进入。账号上传权限、世界可见性、发布状态和目标平台构建均有各自要求。参见 [官方世界创建与发布说明](https://creators.vrchat.com/worlds/creating-your-first-world/)。

## 玩家加载世界

客户端加入一个世界实例时，需要获取适合当前平台的资源版本；已有有效缓存时可以复用，否则下载资源。Unity 随后加载场景、资源和组件，VRChat 根据 Scene Descriptor 等配置放置玩家并启动相应行为。

下载与加载耗时不同：网络速度和压缩包大小影响下载；资源解压、内存占用和初始化工作影响加载。同一包再次进入时可能因缓存减少下载，但不保证省略场景加载。

Unity 编辑器 Play Mode 与 VRChat 客户端的加载路径、输入和可用功能并不完全相同。编辑器内测试通过，仍需要客户端测试。

## 世界与实例

```text
World    世界定义及其可加载资源
Instance 该世界的一次具体多人会话
```

同一个世界可以同时有多个实例。想与朋友见面，需要进入同一个实例，并满足它的访问条件。世界 ID 相同，不表示实例相同。

每位玩家的客户端都运行自己的场景。玩家移动等内置行为有平台提供的同步机制；自定义灯光、分数、按钮状态则需要作者配置相应同步。单独执行 `Light.enabled = false` 不会自动通知所有玩家。

实例内的临时状态也不等于持久化保存。需要跨会话保留的数据必须使用明确的持久化机制；不能从「已上传世界」推断运行中的一切变化都会保存。参见 [官方 Udon 网络同步说明](https://creators.vrchat.com/worlds/udon/networking/)。

## 目标平台分别构建

PC、Android 和 iOS 的资源格式、Shader 支持和设备能力不同。支持多个平台，需要为对应目标构建并上传到同一世界记录，不能只上传 PC 包就认为移动设备能访问。

Quest 和 Android 手机使用 Android 平台资源，但测试条件不同：VR 涉及双眼渲染、头部跟踪和控制器输入，手机使用平面屏幕和触控。手机测试可以发现部分 Android 兼容问题，不能代替 Quest 上的帧率、尺度和交互测试。反方向也不能作性能保证。各设备支持情况以 [官方平台文档](https://creators.vrchat.com/platforms/) 为准。

## Unity 版本为什么需要匹配

AssetBundle、资源导入器、Shader 编译和 SDK 工具都受 Unity 版本影响。VRChat 指定编辑器版本是兼容性要求，不表示所有相邻版本必然产生相同错误。安装与迁移时核对 [当前 Unity 版本](https://creators.vrchat.com/sdk/upgrade/current-unity-version/)，并保留升级前的项目副本。

## 管线与检查位置

```text
Unity 场景和资源
    → SDK 校验与目标平台构建
    ├─ 本地结果 → Build & Test → 本机 VRChat
    └─ 上传结果 → VRChat 内容分发 → 玩家客户端下载
                                      ↓
                          客户端加载场景并加入实例
                                      ↓
                   本地执行 + 已配置的网络状态与事件同步
```

构建报错查 Console 和 SDK 校验；下载失败查资源与网络状态；进入后位置错误查 Spawn 与碰撞；只有某位玩家看到变化则查该变化是否属于本地逻辑或已配置同步。
